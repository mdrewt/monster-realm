# Architecture

How Monster Realm is built today. The reasons behind the load-bearing choices are in
[`docs/DECISIONS.md`](docs/DECISIONS.md); this file describes the shape. Paths are
relative to the repository root.

## The shape in one paragraph

Monster Realm is a multiplayer monster-taming game. It uses a functional core with an
imperative shell, and the server is the authority. One pure Rust crate, `game-core`,
holds every game rule. The authoritative server is a SpacetimeDB module
(`server-module`) whose reducers validate requests, call `game-core`, and write tables.
The browser client (`client/`, TypeScript + PixiJS) subscribes to those tables, renders
them, and predicts its own player's movement by running the same `game-core` code
compiled to wasm (`client-wasm`). A headless driver (`sim-harness`) exercises the
netcode deterministically without a browser.

```text
                 game-core (pure rules + compiled-in RON content)
                 /                    |                        \
     server-module (SpacetimeDB)   client-wasm (wasm-bindgen)   sim-harness
     reducers + tables = truth     prediction exports            headless netcode driver
              |                          |
              +---- subscriptions --->  client/ (TS + PixiJS): store -> predict -> render
```

## Workspace

| Path | What it is |
|---|---|
| `game-core/` | Pure, deterministic rule crate (`#![forbid(unsafe_code)]`) plus `content/` (RON) and `build.rs` (content embed). `src/bin/tiled_import.rs` converts Tiled maps to zone-map RON. |
| `client-wasm/` | `wasm-bindgen` exports over `game-core` for the client; built with `wasm-pack` into `client-wasm/pkg` (gitignored). |
| `server-module/` | The SpacetimeDB module, crate `monster-realm-module` (`cdylib` + `rlib`). |
| `sim-harness/` | Headless multi-client driver with an injected clock, a seed, and a seeded lossy/reordering network link; also the live load driver `src/bin/mr_load_driver.rs`. |
| `client/` | Vite + TypeScript + PixiJS 8 browser client; `src/module_bindings/` is generated by `spacetime generate`. |
| `evals/` | Node checks run by `just eval` (`evals/run.mjs`), with baselines in `evals/baselines/`. |
| `scripts/` | Commit-message and secret checks, playtest verifiers, the smoke-republish script. |
| `ops/` | Deployment recipes: `observability/` (self-hosted monitoring stack) and `auth/` (the OIDC issuer). |

The Cargo workspace (`Cargo.toml`) has five members: `game-core`, `client-wasm`,
`server-module`, `sim-harness`, and `evals/release-overflow-teeth` (a fixture crate
used by the determinism eval). The Rust toolchain is pinned in `rust-toolchain.toml`.

## game-core: the rule layer

`game-core/src/lib.rs` re-exports the public surface. The modules are:

| Module | Rules |
|---|---|
| `world` | Tile maps, `apply_move`, spawn, grass detection; `STEP_MS` (200), `MOVE_QUEUE_CAP` (2), `PARTY_SIZE` (6), `PARTY_SLOT_NONE` (255). |
| `types` | Shared data types (`CharacterState`, `Direction`, `MoveInput`, `Millis`, `TilePos`, `NpcInteraction`). |
| `monster` | Individuality rolls (IVs, nature), stat derivation, levels and XP curve. |
| `combat` | Battle state and turn resolution, damage and accuracy, statuses, abilities, weather, AI, XP rewards, PvP forfeit and challenge staleness. |
| `taming` | Encounter triggers and rolls, recruit chance. |
| `evolution` | Evolution-graph eligibility and the transform. |
| `raising` | Care cooldown (`CARE_COOLDOWN_MS`, 6 h) and focus training. |
| `currency`, `trading` | Balance arithmetic; trade proposal validation, headroom checks, the ordered swap plan. |
| `ranking` | Elo rating update (`INITIAL_RATING` 1000). |
| `npc`, `dialogue`, `quest` | NPC wander decisions, dialogue trees, quest triggers. |
| `accounts` | Deletion grace (`DELETION_GRACE_MS_DEFAULT`, 7 days), export chunk size, tombstone constants. |
| `content` | Parsing, loading and validation of every content registry. |

Rules take their inputs explicitly. Time arrives as `Millis`; randomness arrives as a
seed or as pre-rolled values (`TurnVariance`, `StatusVariance`, individuality seeds).
`clippy.toml` bans wall-clock and unseeded-RNG calls workspace-wide, and `just lint`
treats clippy warnings as errors. Arithmetic is integer-only; the release profile
keeps overflow checks on. The `spacetimedb` Cargo feature adds the `SpacetimeType`
derives the server needs; the client builds without it.

## Content pipeline

Content is data, not code. Each registry is a directory under `game-core/content/`
(`species/`, `skills/`, `items/`, `zones/`, `zone_maps/`, `encounters/`, `npcs/`,
`dialogue_trees/`, `quests/`, `heal_locations/`, `shops/`, `abilities/`,
`evolution_paths/`) of `*.ron` part files, plus the single file `type_chart.ron`.

1. **Embed.** `game-core/build.rs` lists each registry directory, sorts the `*.ron`
   files by name, and generates a static of `(filename, include_str!(...))` pairs. A
   missing registry directory fails the build. Part files are prefixed with a number
   (`000-core.ron`, `050-wave2.ron`, ...), so load order is stable and new content
   lands in new files.
2. **Parse and validate.** `load_*` parses the parts and concatenates them;
   `validate_content` and the per-registry validators check cross-references and
   ranges. Ids are stable and append-only; the `append-only-ids` eval keeps a
   baseline per registry in `evals/baselines/*-ids.json`.
3. **Seed.** On the server, `sync_content` (owner-only) and `init` call
   `content::sync_content_inner`, which reseeds the public content tables
   (`species_row`, `skill_row`, `item_row`, `zone_def`, `shop_row`, `shop_item_row`,
   `heal_location_row`, `npc`, `evolution_path`, `type_relation_row`), the private
   `encounter` table, and the NPCs' `character` rows whenever
   `config.content_version` differs from `CONTENT_VERSION` in
   `server-module/src/lib.rs`. It also reconciles one movement schedule row per zone.
   A reseed also re-derives every existing monster: stats are recomputed from the new
   species base stats with the monster's own IVs, EVs, Nature and level, `current_hp`
   is clamped down to the new maximum (a reseed never heals), and the `monster_pub`
   copy is rewritten with the species' current tier (`content.rs`
   `recompute_monster_derived_fields`). A missing species row is logged and skipped.
   Parsed registries are cached in `LazyLock` statics (`server-module/src/content_cache.rs`).
4. **Version.** The `content-version` eval hashes every file under `game-core/content/`
   (raw bytes, so comment edits count) and compares the hash and `CONTENT_VERSION`
   with `evals/baselines/content-hash.json`. After a content change, bump
   `CONTENT_VERSION` first, then regenerate the baseline with the command the eval
   prints on failure.
5. **Client.** The client gets zone maps from the wasm `zone_map()` export and
   the rest from the seeded public tables. The one exception is dialogue text:
   `client/src/ui/dialogueContent.ts` mirrors `game-core/content/dialogue_trees/`,
   and a contract keeps the two identical. A server test renders the shipped trees
   into `evals/baselines/dialogue-trees.txt` (regenerate with
   `MR_BLESS_DIALOGUE_TREES=1 cargo nextest run -p monster-realm-module dialogue_trees_contract`),
   and `dialogueContent.contract.test.ts` requires the client mirror to render
   byte-equal to it. A dialogue edit therefore changes the RON, the TS mirror and the
   contract file together.

## client-wasm: the prediction boundary

`client-wasm/src/lib.rs` exports `apply_move`, `predict_move`, `predict_tick`,
`set_active_zone`, `zone_map`, `evolution_eligibility`, `interact_candidates_coded`, and
constant accessors (`step_ms`, `move_queue_cap`, `party_size`, `party_slot_none`, `talk_range`,
`max_trade_monsters_per_side`, `deletion_grace_ms_default`, the last returned as a
JS `BigInt`). Values cross the boundary as serde values (`serde-wasm-bindgen`). The
module parses zone maps once per instance and caches the active zone's tile map
until `set_active_zone` changes it. The parity evals (`prediction-parity`,
`movement-parity`, `js-path-parity`) run the native and wasm builds on the same
inputs and require identical output. `feature-isolation` checks that the client
crate never pulls in the server-only feature.

## server-module: the authority

### Layout

`server-module/src/lib.rs` wires the domain modules and holds the three lifecycle
reducers plus `sync_content`. Each domain module owns its reducers and the tables it
writes:

| Module | Reducers |
|---|---|
| `movement` | `join_game`, `enqueue_move`, `set_move`, `clear_queue`, scheduled `movement_tick` |
| `battle` | `start_battle`, `submit_attack`, `swap_active`, `use_battle_item`, `flee` (+ dev-only `start_wild_battle`) |
| `taming` | `attempt_recruit` (+ dev-only `grant_bait`) |
| `raising` | `care`, `train`, `essence_train`, `consume_crystalized_essence`, `heal_party` |
| `evolution` | `evolve`, `ack_evolution_notices` |
| `monster_mgmt` | `set_nickname`, `set_party_slot` |
| `economy` | `buy`, `sell` |
| `npc` | `talk`, `advance_dialogue`, `dismiss_dialogue` |
| `trading` | `propose_trade`, `respond_trade`, `confirm_trade`, `cancel_trade`, scheduled `trade_offer_reaper` |
| `pvp` | `challenge_pvp`, `accept_challenge`, `decline_challenge`, `cancel_challenge`, `submit_pvp_action`, scheduled `pvp_deadline_reaper` and `battle_challenge_reaper` |
| `ranking` | `set_profile_name` |
| `accounts` | `start_guest_claim`, `complete_guest_claim`, `delete_account`, `cancel_account_deletion`, scheduled `guest_claim_reaper` and `account_deletion_reaper` |
| `privacy` | `request_data_export`, scheduled `export_bundle_reaper` |
| `observability` | scheduled `mr_heartbeat` |
| `playtest` | scheduled `playtest_reaper` |

Supporting modules have no reducers: `schema` (tables, views, the data-lifecycle
manifest), `guards` (shared validation), `marshal` (row ⇄ `game-core` conversion,
`now_ms`), `inventory` (the single `grant_item` insert path), `content` and
`content_cache`.

A reducer checks `ctx.sender()` and the request, calls `game-core`, and writes. It
returns `Err` to refuse, which rolls back the whole transaction, and logs the refusal
as a JSON line through `guards::log_reject`. Scheduled reducers first check
`ctx.sender() == ctx.database_identity()`, so clients cannot call them.

### Lifecycle

- `init` (first publish only) records the publisher as `config.owner_identity`, seeds
  content, reconciles zone schedules, and arms the reapers and heartbeat.
- `sync_content` does the same reseed for the owner on later publishes. It refuses
  other callers.
- `on_connect` records the connection in the private `player_session` table and, for
  a JWT from an allowed issuer, creates or updates the caller's `account` row.
  Connections without an account are accepted.
- `on_disconnect` deletes that connection's session row. If the identity has no
  other live connection, it resolves the identity's trades, PvP battles, wild battles
  and challenges (`resolve_all_live_interactions`), then deletes the conversation,
  character and player rows.

### Movement

Movement is paced by the server, per zone. A client sends intent (`enqueue_move`,
`set_move`, `clear_queue`) tagged with a strictly increasing `seq`;
`guards::authorize_move` rejects a stale seq and records the new one as
`player.last_input_seq` (the acknowledgement the client reconciles against). The
character's queue (`character.move_queue`, capped at `MOVE_QUEUE_CAP`) is public so
the owner can reconcile against what is left. Each zone has an interval schedule row
that runs `movement_tick` every `STEP_MS`. A tick drains at most one move per
character through `game_core::apply_move`, moves NPCs with `npc_decide`, accrues
Quality-Time, and rolls grass encounters. A character whose player is in a battle
drains nothing, and `enqueue_move`/`set_move` reject new moves during a battle.

### Battles, trades and the rest

- **PvE.** A grass encounter starts a wild battle and stores the wild's
  individuality seed in the private `battle_wild` table. Turns resolve in
  `game-core` with `TurnVariance::from_ctx_random(ctx.random())`. A recruit rebuilds
  the exact individual from the seed. After a battle ends, only the latest finished
  battle per player is kept.
- **PvP.** Challenges are public rows with a 120 s TTL. Each side's secret move is a
  private `battle_action` row. A turn resolves when both moves are in, or a 60 s
  deadline reaper forfeits the side that did not act. Ranked results update the
  public `profile` table.
- **Trading.** Offers are public `trade_offer` rows with a one-hour TTL
  (`TRADE_OFFER_TTL_MS`). Offered assets stay where they are, and guards stop them
  being spent, sold or evolved while the offer is open. `confirm_trade` checks
  receiver headroom and applies an ordered swap plan (debits first).
- **Raising and economy.** Care, training, essence and healing live in `raising`;
  every balance change goes through `economy::grant_currency`/`spend_currency`, and
  every inventory insert through `inventory::grant_item`, which keeps one stack per
  owner and item.
- **Evolution.** See the evolution entry in `docs/DECISIONS.md`: authored edges in the
  public `evolution_path` table, one shared eligibility query, and automatic evolution
  only when exactly one edge qualifies.

### Working with SpacetimeDB

- Syntax is 2.x: `#[spacetimedb::table(accessor = x)]`, `ctx.sender()`,
  `ctx.database_identity()`. `.claude/skills/spacetimedb-reducer` has the details.
- `#[table(accessor = x)]` generates a crate-private trait `x`; a module that uses
  `ctx.db.x()` for a table declared in another module has to import that trait
  (for example `use crate::schema::config;`). `cargo check` reports a missing import.
- A scheduled table has to be declared in the same module as its reducer so the
  `scheduled(reducer)` attribute resolves; that is why the reaper schedule tables live
  next to their reducers instead of in `schema.rs`.
- Time columns are `i64` milliseconds: `marshal::now_ms` converts
  `ctx.timestamp.to_micros_since_unix_epoch()`.
- A one-shot `spacetime call` opens its own connection and closes it afterwards, so
  it runs `on_connect`/`on_disconnect` around the reducer. A presence row created by
  such a call is deleted when it returns.
- Subscribing to a private table from the client fails the whole subscription batch.
  Clients subscribe to the owner-scoped view instead.
- Schema changes on a live database must be additive (append columns with a
  `#[default]`); see `docs/DECISIONS.md`.

## Schema and privacy model

All tables are declared in `server-module/src/schema.rs`, except the scheduled tables
(which live with their reducers) and `playtest_event` (`playtest.rs`). Visibility is
part of the schema:

| Class | Tables | Client read path |
|---|---|---|
| Public content | `species_row`, `skill_row`, `item_row`, `type_relation_row`, `zone_def`, `shop_row`, `shop_item_row`, `heal_location_row`, `npc`, `evolution_path`, `config` | direct subscription |
| Public world state | `character`, `player`, `profile`, `trade_offer`, `battle_challenge`, `player_quest` | direct subscription |
| Private, owner-readable | `monster_pub`, `inventory`, `player_wallet`, `player_conversation`, `account`, `pending_evolution_notice`, `export_bundle` | views `my_monster_pub`, `my_inventory`, `my_wallet`, `my_conversation`, `my_account`, `my_pending_evolution_notices`, `my_export_bundle` |
| Private, participant-readable | `battle` | view `my_battle` (either side) |
| Private, server only | `monster`, `encounter`, `battle_wild`, `battle_action`, `player_dialogue_state`, `heal_cooldown`, `guest_claim`, `player_session`, all schedule tables | none |

A view takes only its context and filters on `ctx.sender()` through an index. That
body is the whole security boundary.

- **`monster` vs `monster_pub`.** `monster` holds the hidden genes (IVs, EVs, nature)
  and server-side counters. `monster_pub` is the safe projection (derived stats, HP,
  party slot, tiers, essence). The server writes both together; the owner reads
  `monster_pub` through `my_monster_pub`. Other players' monsters are not delivered
  at all.
- **`inventory`.** Item counts are private because scouting another player's stock is
  a competitive leak. `my_inventory` returns only the caller's stacks. Reducers read
  the table directly.
- **`battle`.** Only the two participants see a battle, through `my_battle`. A
  practice battle (same identity on both sides) appears once. `BattleState` carries
  derived stats only, never genes.
- **Accepted exposures.** `trade_offer` is public so both parties can see it, so the
  amounts offered reveal a lower bound on the offering player's balance. The display
  cards in an offer carry public-projection fields only.
- **Data lifecycle.** `schema::DATA_LIFECYCLE_MANIFEST` gives every table a deletion
  policy (Erase, Anonymize, ViaJoin, NotOwned), a written basis, and an `exportable`
  flag. A test in `accounts_tests.rs` fails if a table is missing from it or listed
  but gone.

The `battle-schema-snapshot` and `spacetime-type-snapshot` evals record every table's
columns and every nested `SpacetimeType` in `evals/baselines/`, so an unplanned
migration-breaking change fails `just eval`. `client-surface-privacy` checks the
generated bindings against the allowed client-visible tables and client-callable
reducers (`evals/baselines/client-visible-tables.json`,
`client-callable-reducers.json`). Generated bindings are never edited by hand;
`just gen` regenerates them, and `bindings-drift` fails when they are stale.

## Client

`client/src/main.ts` wires everything; the logic lives in small modules, mostly pure
with thin shells.

### Connection and store

`net/connection.ts` builds the SpacetimeDB connection (URI and database from
`VITE_STDB_URI`/`VITE_STDB_DB`; a production build refuses the dev-default database,
`net/connectionConfig.ts`). It subscribes to the public tables and the owner-scoped
views in one batch; the character subscription covers all zones, and off-zone
characters are filtered at render time. The SDK fires per-row callbacks.
`net/batch.ts` coalesces a transaction's callbacks within one microtask so the store
flushes once per burst, and the predictor reconciles against a consistent snapshot.
`net/rowConvert.ts` and `convert/convert.ts` convert SDK rows (tagged unions,
`bigint` ids) into store and wasm shapes, explicitly and without abstraction.

Views behave differently from tables on the client. None of the module's views
declares a primary key, so the SDK never fires `onUpdate` for a view row: a change
arrives as an unordered delete and insert. Before each flush, `connection.ts` rebuilds
every view-backed collection (`my_monster_pub`, `my_battle`, `my_inventory`, ...) from
the SDK's cache rather than applying those row events one by one.

`net/store.ts` is a read-only mirror of the subscription. Only the connection adapter
writes to it; the predictor and renderer only read (`server → store → render`). It
keeps up to four timestamped snapshots per character for interpolation and a
per-character jitter estimate.

Reconnect uses exponential backoff from 1 s to 30 s (`prediction/reconnectPolicy.ts`).
The SpacetimeDB token for an anonymous identity is stored in `sessionStorage`
(`net/authToken.ts`), so an identity survives a reload but not closing the tab, and a
second tab is a separate identity. After two token rejections since the last
successful connect, the client stops sending the stored token (it never deletes it) and
connects anonymously. If that connect succeeds, `onConnected` stores the new token over
the old one; a network failure never counts as a rejection, so an outage cannot cost
the player their identity. Sign-in is OIDC (authorization code with
PKCE, `net/oidc.ts`) against the issuer in `VITE_MR_OIDC_ISSUER`.

### Prediction and reconciliation

`prediction/predictor.ts` runs the wasm `apply_move` locally so a keypress moves the
player immediately:

1. **Intent.** `enqueue`, `setMove` and `clearQueue` record a queue operation with the
   next `seq` and return it for sending. `enqueue` refuses past `MOVE_QUEUE_CAP` and
   at 16 unacknowledged operations.
2. **Drain.** Each frame, `drain(now)` applies due moves at `STEP_MS` cadence, at most
   the queue cap per drain. After a long gap (a backgrounded tab) it reports `snapped`
   so the renderer jumps instead of replaying.
3. **Reconcile.** On each flushed batch, `reconcile` drops acknowledged operations
   (`seq <= player.last_input_seq`), rebuilds the queue from the server's
   `move_queue`, replays the pending operations, resets to the authoritative position,
   and drains. It reports whether the corrected tile differs from the prediction.
4. **Rejections.** A rejected intent is removed with `dropRejected(seq, epoch)`,
   followed by a forced reconcile. The epoch makes a rejection addressed to a
   discarded predictor (after a warp or reconnect) a no-op, and rebuilt predictors
   start above the highest seq already sent.

Held keys (`prediction/heldKeys.ts`) keep a most-recent-first stack of held
directions. The frame loop re-issues the active direction only after it has been held
150 ms and only when the predictor has no outstanding steps. OS key-repeat is ignored.
A zone warp (`switchZone` in `main.ts`) rebuilds prediction state but keeps the held
stack.

### Rendering

`render/` splits into pure cores and a Pixi shell:

- `slideClock.ts` animates the own character on a local clock keyed to target-tile
  changes. It ignores the server's `move_started_at`, which is re-stamped every tick
  and would restart the slide.
- `interpolation.ts` renders remote characters in the past between buffered
  snapshots, with an adaptive delay, holding at the newest snapshot rather than
  extrapolating. It also has a reduced-motion path.
- `renderResolver.ts` sends each character to the right one of those two and snaps
  the own character when the authoritative target is more than one tile away.
- `map.ts` parses the tile map once from the wasm `zone_map()` value; `camera.ts`
  follows the player and centres maps smaller than the viewport; `viewport.ts` picks
  an integer device scale; `viewRegistry.ts` pools one sprite per entity and tears it
  down on despawn.
- `world.ts`, `characterView.ts` and `placeholderAssets.ts` are the Pixi shell.
  Tiles are drawn at `TILE_PX` (32). Placeholder art draws facing and action as
  monochrome shapes, so neither depends on colour.

The frame loop in `main.ts` (`requestAnimationFrame`) drains the predictor, resolves
positions, and draws.

### UI

Input is a console-style pipeline of virtual buttons (`input/buttons.ts`: the D-pad, A, B,
X, Y, LB, RB, Start, Select). Two sources feed it: `input/keyboardSource.ts` maps keys through
the remappable binding table (`input/bindings.ts`, saved by `input/bindingStore.ts`, drawn by
`input/glyphs.ts`), and `input/pointerSource.ts` is ONE dispatcher on `#game-screen`. A click on
the canvas at the world base is A (no coordinates). A click on a row of the top frame is a seek:
the D-pad presses that walk that list's cursor there, then A. The first press is a probe: if the
clicked list's cursor did not move as planned, it is undone and nothing is activated. A click on a tab is LB/RB. A right-click, or a touch long-press
(`input/longPress.ts`, 500 ms within 10 px, with a fill ring), is B, or cancels a remap capture.
A hint-bar chip presses its button. The mouse hovering a row moves the cursor there. Both sources
hand button edges to `input/router.ts`, which decides walking, menu navigation or a screen button
from the context on top. Two clicks skip the router: a main-menu row (the menu's own pick) and the
dialogue's choice and shop buttons.

The context stack (`ui/contextStack.ts`) is the base (world or battle) plus the frames above it.
`SCREEN_POLICY` says what a battle or a server conversation closes, and `reconcile` mirrors server
truth into the stack. Each frame's screen adapter (`ui/screens/`, keyed by frame in
`SCREEN_ADAPTERS`) turns a button into a nav step or a command. `main.ts` runs commands through
`dispatch` and applies stack changes through `applyStack`. `ui/overlayRegistry.ts` still decides
which overlay may open over which (`canOpen`), its accessibility metadata (`OVERLAY_A11Y`) and
which are visible. Frames are built from `ui/frame.ts` and `ui/navRender.ts` inside
`#game-screen`'s frame layer. The hint bar (`ui/hintBarModel.ts`, `ui/hintBar.ts`) and Help
(`ui/helpModel.ts`) are generated from the context table, the live bindings and the catalog. At
the world base, A acts on the target that the wasm `interact_candidates_coded` export picks (an NPC, a
shop or a heal tile within talk range). The server re-checks the range.

Strings come from `ui/i18n/`: a `MessageId` union, total catalogs for `en` and `fr`, a
resolver whose `t()`/`tf()` throw on a missing key, CLDR plural rules, and boot-time
locale negotiation from `navigator.languages` (`locale.ts`). Accessibility is
first-class: status badges carry text tokens from `game-core`'s `A11Y_TOKENS`, focus
is trapped in modals (`focusTrap.ts`), announcements go through live regions
(`liveRegion.ts`, `announcements.ts`), and `Element.animate` is banned
(`client/lint/no-waapi.grit`) because it ignores `prefers-reduced-motion`.

### Diagnostics

- `F9` downloads a bug bundle (`ui/bugBundle.ts`) assembled locally from the recent
  event ring (`eventRing.ts`), captured errors (`errorRing.ts`), a projected store
  snapshot without names, and the build stamp (git short SHA and build time injected
  by `vite.config.ts`, `net/buildInfo.ts`). Nothing is sent over the network.
- Uncaught errors show a non-blocking toast that `B` at the world base or `F8` dismisses.
- DEV builds expose debug hooks (`__game`, `__mrTrade`, `__mrPvp`) inside an
  `import.meta.env.DEV` branch; `scripts/verify-build-hooks.mjs` checks that a
  production bundle contains none.
- `VITE_MR_DEVLOG` enables a DEV console log of outbound reducer calls
  (`net/devLog.ts`).
- Client telemetry (`observability/`) exports OpenTelemetry metrics over OTLP/HTTP to
  `VITE_MR_OTLP_ENDPOINT` when set. It fails silently, loads the SDK only when
  enabled, and labels metrics with a small allowlist of attributes.

## Accounts lifecycle

- **Anonymous by default.** Every connection has a SpacetimeDB identity. Game data is
  keyed by that identity; there is no account row and no PII.
- **Signing in.** With OIDC configured on the client, sign-in redirects to the issuer
  and reconnects with the resulting JWT. `on_connect` creates an `account` row only
  when the token's issuer and audience match `ALLOWED_ISSUERS`/`ALLOWED_AUDIENCE`
  (`server-module/src/accounts.rs`). Those constants still hold the fail-closed
  `.invalid` placeholder, so no account can be created until a real issuer is
  deployed and the constants are changed. `ops/auth/README.md` has the deployment
  steps and the client build variables (`VITE_MR_OIDC_ISSUER`,
  `VITE_MR_OIDC_CLIENT_ID`, `VITE_MR_OIDC_REDIRECT_URI`).
- **Claiming guest progress.** The client mints a 64-hex-character claim code
  (`net/claimCode.ts`), stores it per tab, and calls `start_guest_claim(code)` as the
  guest before redirecting to sign-in. The server stores it in the private
  `guest_claim` table with a 15-minute TTL and a one-shot reaper. After sign-in, the
  account calls `complete_guest_claim(code)`. Guards run in order: signed in, holds
  an account, not deleting, not already claimed, well-formed code, live claim, not
  expired, not its own session, guest no longer connected, neither side in a battle,
  and the account owns no game data yet. Then `rekey_all` moves the guest's persistent
  game data (monsters and their public projection, evolution notices, inventory,
  quests and dialogue state, heal cooldown, wallet, profile) onto the account, the
  guest's export bundles are purged, the code is consumed, and
  `claimed_from`/`claimed_at_ms` are stamped. Session and in-flight rows (player,
  conversation, sessions, battles, trades, challenges) are not moved.
  "Owns no game data" works because `join_game` is a reducer the client calls, not
  part of `on_connect`: on a signed-in connection with an unconsumed claim code
  stored, `net/connection.ts` skips `join_game` and calls `complete_guest_claim`
  first. It joins only once no unconsumed code remains, or the player declines the
  claim. An account that already played before claiming fails the claim with "already
  has game data".
- **Deletion.** `delete_account` sets `PendingDeletion` and arms a reaper 7 days out;
  `cancel_account_deletion` reverses it and declines trade offers made to the account
  after it asked to be deleted. While deletion is pending, the account cannot start
  new battles, trades, challenges or other writes (`guards::require_not_deleting`),
  but commitments made before the request can still finish. The reaper resolves live
  interactions, forces ongoing battles to a terminal result, erases or anonymises
  every table per the manifest, and stamps `terminal_at_ms`. A later sign-in with the
  same identity starts a fresh account.
- **Export.** `request_data_export` writes the caller's exportable tables as JSON
  chunks into the private `export_bundle` table, read back through
  `my_export_bundle`. It enforces a per-caller cooldown, a unique creation stamp per
  bundle, and a global live-row cap (smaller for callers without an account, smaller
  still without a wallet). An hourly reaper deletes bundles older than 7 days. The
  client assembles the chunks (`ui/exportAssembly.ts`) and offers the file for
  download from the privacy overlay, which opens from the account overlay (`C`).
- **Ranked PvP** will require accounts on both sides once a real issuer is set
  (`pvp.rs` `ranked_account_gate`). Until then the gate is inactive.

## Observability

- **Server.** The module emits JSON log lines. New code uses `observability::mr_log`;
  refusals go through `guards::log_reject`. A 60 s `mr_heartbeat` logs the deployed
  content version and writes nothing. The module never measures time itself or makes
  outbound calls; the SpacetimeDB host exposes `/v1/metrics` and writes module logs
  to files.
- **Stack.** `ops/observability/` is a Docker Compose stack on the host network,
  bound to loopback: Prometheus scrapes the host and node_exporter; Grafana Alloy
  tails the module logs into Loki and receives browser OTLP through Caddy, forwarding
  traces to Tempo and metrics to Prometheus; `mr-trace-relay` rebuilds server-side
  spans from paired log lines; Grafana (behind Caddy) queries all of them and handles
  alerting. Configuration checks run in `just test` (the `stack-config-checks` and
  relay node suites) and `just observability-validate` (upstream validators in the
  pinned images). Operations are in `docs/runbooks/observability-dr.md`.
- **Playtest capture.** The private `playtest_event` table records recruit attempts
  (`server-module/src/playtest.rs`); `playtest_reaper` runs every 5 minutes and keeps
  it under a 7-day TTL and a 20 000-row cap. `just playtest-report` summarises it.
- **Load.** `sim-harness`'s `mr_load_driver` connects many WebSocket clients to a
  live module and reads the breaking point from `/v1/metrics`. It never runs in CI.
