# Architecture

How Monster Realm is built today. The reasons behind the load-bearing choices are in
[`docs/DECISIONS.md`](docs/DECISIONS.md); this file describes the shape. Paths are
relative to the repository root.

## The shape in one paragraph

Monster Realm is a multiplayer monster-taming game. It uses a functional core with an
imperative shell, and the server is the authority. One pure Rust crate, `game-core`,
holds every game rule. The authoritative server is a SpacetimeDB module
(`server-module`) whose reducers validate requests, call `game-core`, and write tables.
The browser client (`client/`, TypeScript + PixiJS) subscribes to those tables, renders
them, and predicts its own player's movement by running the same `game-core` code
compiled to wasm (`client-wasm`). A headless driver (`sim-harness`) exercises the
netcode deterministically without a browser.

```text
                 game-core (pure rules + compiled-in RON content)
                 /                    |                        \
     server-module (SpacetimeDB)   client-wasm (wasm-bindgen)   sim-harness
     reducers + tables = truth     prediction exports            headless netcode driver
              |                          |
              +---- subscriptions --->  client/ (TS + PixiJS): store -> predict -> render
```

The Cargo workspace (`Cargo.toml`) has five members: `game-core`, `client-wasm`,
`server-module`, `sim-harness`, and `evals/release-overflow-teeth` (a fixture crate

`server-module`, `client-wasm` and `sim-harness` take `game-core` as a path dependency;
only `server-module` turns on its `spacetimedb` feature.

## game-core: the rule layer

`game-core/src/lib.rs` re-exports the public surface. The modules are:

| Module | Rules |
|---|---|
| `world` | Tile maps, `apply_move`, spawn, grass detection; `STEP_MS` (200), `MOVE_QUEUE_CAP` (2), `PARTY_SIZE` (6), `PARTY_SLOT_NONE` (255). |
| `types` | Shared data types (`CharacterState`, `Direction`, `MoveInput`, `Millis`, `TilePos`, `NpcInteraction`). |
| `monster` | Individuality rolls (IVs, nature), stat derivation, levels and XP curve. |
| `combat` | The types stored in `Battle.state` and the content rows, and the rules a production path calls: the damage formula and accuracy check, the type chart, lead selection, the status countdown, the XP rules, and the PvP forfeit and challenge rules. The rest (the turn driver in `combat/resolve.rs`, the enemy skill picker, the entry-ability hooks, the weather chip and countdown) has no production caller; `docs/refactors/combat-carried-rules.md` lists what is left to remove and in what order. Where a carried rule's signature takes the 1v1 `BattleState`, `tactics/` states it once. |
| `tactics` | Tactical-battle rules (M-battle-tactics): `geometry` (Manhattan metric, line of sight, the one skill target-set function, flank), `movement` (stride bands, terrain × class weights, Dijkstra pathing with an explicit `(cost, y, x)` tie-break, disengage), `map` (the battle-map validator), `tuning` (`TacticsTuning`, `BattleKind`), `economy` (AP costs, Exert, Guard), `initiative`, `resolve` (`TacticalState` and the damage pipeline), `upkeep`, `outcome` (KO sweep, adjudication), `types` (the storage enums `QueuedAction`, `TurnState`, `Phase`), `events` (the `battle_event` payload), `clock`, `queue` (`TacticalBattle`: the submit gate and executor), `ai`, `encounter`, `recruit`, `rewards`, and `content` (the sidecar registries and lints). `tactics::golden` runs a shared JSON fixture natively and through the `tactics_golden` wasm export to prove native = wasm. |
| `taming` | dev-only `grant_bait`; the tactical recruit is a `submit_queue` entry (the 1v1 `attempt_recruit` is deleted since bt-17) |
| `evolution` | Evolution-graph eligibility and the transform. |
| `raising` | Care cooldown (`CARE_COOLDOWN_MS`, 6 h) and focus training. |
| `currency`, `trading` | Balance arithmetic; headroom checks, the ordered swap plan; the offer proposal and role rules, which no reducer calls; the trade-session rules (`trading::session`: eligibility, edits and confirms by revision, the per-side check, the execute verdict, snapshot drift, arrival slots). |
| `ranking` | Elo rating update (`INITIAL_RATING` 1000). |
| `npc`, `dialogue`, `quest` | NPC wander decisions, dialogue trees, quest triggers. |
| `accounts` | Deletion grace (`DELETION_GRACE_MS_DEFAULT`, 7 days), export chunk size, tombstone constants. |
| `content` | Parsing, loading and validation of every content registry. |

Rules take their inputs explicitly. Time arrives as `Millis`; randomness arrives as a
seed or as pre-rolled values (individuality seeds; `StatusVariance`, which the tactical
upkeep fills from the battle's roll stream; `combat`'s `TurnVariance`, which no shipped
caller uses). On the server, `now_ms`
(`server-module/src/marshal.rs`) turns `ctx.timestamp` into the milliseconds a rule
takes as `Millis`, and seeds are drawn from `ctx.random()`. A tactical battle keeps its seed in
the private `battle_secret` row and draws each target's accuracy and variance rolls
from `splitmix64(seed ^ action_seq)` (`tactics::resolve::draw_rolls`).
`clippy.toml` bans wall-clock and unseeded-RNG calls workspace-wide, and `just lint`
treats clippy warnings as errors. Arithmetic is integer-only; the release and bench
profiles keep overflow checks on. The `spacetimedb` Cargo feature adds the `SpacetimeType`
derives the server needs; the client builds without it.

Damage is `combat::damage::calc_damage`, with `u64` intermediates and a `u16` result:
`base = (2·level/5 + 2)·power·attack/defense/50 + 2`, then STAB ×3/2, type
effectiveness ×{0,5,10,20}/10 (0 returns an immune hit before any other term), the
variance roll in `85..=100` /100, the weather multiplier as an integer
numerator/denominator, and a floor of 1. The tactical pipeline
(`tactics::resolve::damage_pipeline`) passes no weather, then applies flank and Guard
and floors any non-immune hit at 1 again.

**Tactical engine.** `tactics::queue::TacticalBattle` is the submit gate and the
executor. At pop, `validate_at_pop` checks each entry; the first that fails and every
later one are wasted and reported once as `PlanHalted{unit, idx, reason_kind}`,
and control returns live (`Waiting(U)`) to a player-owned conscious unit with at
least `min_action_cost` AP (the cheapest of `light_cost`, `move_stride_cost` and
`item_cost`, 2 at the design's numbers), else the turn ends committed; the floor
bounds a unit-turn to 3 windows (6 → 4 → 2). A live submit whose first entry
fails is refused as `SubmitError::InvalidNow`. The idle clock (`tactics::clock`)
keeps its windows and strike counts per side, so in Practice one player holds both;
a PvP-ruleset window is `pvp_window_ms` (30 s, `game-core/content/tactics_tuning.ron`)
and the `autopass_forfeit`-th (4th) auto-pass forfeits. A submit that lands after its
deadline but before the fire commits is accepted; the fire then finds the window closed
and is a no-op. The executor reaches the planner, inventory, recruit headroom and the
Item/Recruit/Flee resolution only through the `Hooks` trait (`plan_ai`, `item_count`,
`take_item`, `recruit_headroom`, `validate_delegated`, `resolve_delegated`);
`resolve_delegated` may return only `RecruitResult`, `Awards` and `Status` payloads, and
the terminal sweep (`outcome::settle`) decides the outcome after it.

The tactical conventions: only side A of a wild battle is player-owned
(`queue::is_player_owned`) and it holds round-1 tie priority
(`initiative::round1_priority`); the round-1 PvP priority coin and the
adjudication coin (`outcome::adjudicate`) read `splitmix64(..) & 1` with 0
→ A; `BattleKind::uses_pvp_rules` (`tactics/tuning.rs`) is the one mapping
that gives Practice the PvP ruleset; `outcome::check_battle_end` makes a wild
mutual wipe `SideBWins` by `FixedOrder`; `resolve::draw_rolls` draws an accuracy
then a variance roll for every target; `resolve::resolve_attack` judges flank
on the board captured before the attack; freeze thaw rolls come off the same
`splitmix64(seed ^ action_seq)` stream (`resolve::draw`, `upkeep::run_upkeep`); the
wild round cap fires on `round >= wild_round_cap` (`upkeep.rs`). The shared fixture
`game-core/tests/fixtures/tactics_golden.json` pins `draw_rolls` natively and through the
`tactics_golden` wasm export.

The wild planner `tactics::ai::plan(state, unit, stance, spawn, t)` takes no
seed or RNG parameter, and `ai_tests.rs` pins its signature as a `fn` pointer
type. `View::of` builds the private `View` (no `seed`, `action_seq` or budget
field) that every stance helper reads, and `admissible` costs each candidate from
`TurnBudget::fresh(t)` through `plan_cost`, which folds the gate's `spend`. The executor
hands `Hooks::plan_ai` the `public_view` (`seed` and `action_seq` zeroed), halts
anything but `Move`/`Skill`/`EndTurn` as `BadShape`, and runs every entry, the trailing
`EndTurn` included, through `validate_at_pop` (`queue.rs` `start_turn`, `execute`). The
planner calls `movement::path_costs` (the Dijkstra behind the gate's `find_path`),
`target_set`, `disengage_taxed`, `stride_points` and `validate_unit`. The `View`'s units
are `&TacticalUnit`, so `budget` stays reachable: the seed- and budget-blindness tests
and the executor proptest (no `PlanHalted` on generated battles) in `ai_tests.rs` catch
a regression.

## Content pipeline

Content is data, not code. Each registry is a directory under `game-core/content/`
(`species/`, `skills/`, `items/`, `zones/`, `zone_maps/`, `encounters/`, `npcs/`,
`dialogue_trees/`, `quests/`, `heal_locations/`, `shops/`, `abilities/`,
`evolution_paths/`) of `*.ron` part files, plus the single file `type_chart.ron`.

1. **Embed.** `game-core/build.rs` lists each registry directory, sorts the `*.ron`
   files by name, and generates a static of `(filename, include_str!(...))` pairs. A
   missing registry directory fails the build. Part files are prefixed with a number
   (`000-core.ron`, `050-wave2.ron`, ...), so load order is stable and new content
   lands in new files.
2. **Parse and validate.** `load_*` parses the parts and concatenates them;
   `validate_content` and the per-registry validators check cross-references and
   ranges. Ids are stable and append-only; the `append-only-ids` eval keeps a
   baseline per registry in `evals/baselines/*-ids.json`.
3. **Seed.** On the server, `sync_content` (owner-only) and `init` call
   `content::sync_content_inner`, which reseeds the public content tables
   (`species_row`, `skill_row`, `item_row`, `zone_def`, `shop_row`, `shop_item_row`,
   `heal_location_row`, `npc`, `evolution_path`, `type_relation_row`), the private
   `encounter` table, and the NPCs' `character` rows whenever
   `config.content_version` differs from `CONTENT_VERSION` in
   `server-module/src/lib.rs`. It also reconciles the movement schedule: a row for a
   zone that no longer exists is removed, and a zone a player stands in is armed if
   its row is missing.
   A reseed also re-derives every existing monster: stats are recomputed from the new
   species base stats with the monster's own IVs, EVs, Nature and level, `current_hp`
   is clamped down to the new maximum (a reseed never heals), and the `monster_pub`
   copy is rewritten with the species' current tier (`content.rs`
   `recompute_monster_derived_fields`). A missing species row is logged and skipped.
   Parsed registries are cached in `LazyLock` statics (`server-module/src/content_cache.rs`).
4. **Version.** The `content-version` eval hashes every file under `game-core/content/`
   (raw bytes, so comment edits count) and compares the hash and `CONTENT_VERSION`
   with `evals/baselines/content-hash.json`. After a content change, bump
   `CONTENT_VERSION` first, then regenerate the baseline with the command the eval
   prints on failure.
5. **Client.** The client gets zone maps from the wasm `zone_map()` export and
   the rest from the seeded public tables. The one exception is dialogue text:
   `client/src/ui/dialogueContent.ts` mirrors `game-core/content/dialogue_trees/`,
   and a contract keeps the two identical. A server test renders the shipped trees
   into `evals/baselines/dialogue-trees.txt` (regenerate with
   `MR_BLESS_DIALOGUE_TREES=1 cargo nextest run -p monster-realm-module dialogue_trees_contract`),
   and `dialogueContent.contract.test.ts` requires the client mirror to render
   byte-equal to it. A dialogue edit therefore changes the RON, the TS mirror and the
   contract file together. No content table has a locale column; the text a player
   reads is localized in the client catalog (`client/src/ui/i18n/`).

Tactical content lives in four registries keyed by another row's id
(`tactics_skills/`, `tactics_species/`, `tactics_items/`, `tactics_zones/`), beside
`battle_maps/` and `tactics_tuning.ron`. `validate_tactics_content`
(`game-core/src/tactics/content.rs`) joins and lints them; the `game-core` tests run it
over the shipped content, and `sync_content_inner` runs it in its validate phase, before
any write. `docs/refactors/tactics-content.md` lists the slices that move each field
onto the row it describes.

## client-wasm: the prediction boundary

`client-wasm/src/lib.rs` exports six families. Movement prediction: `apply_move`,
`predict_move`, `predict_tick`. Zone maps: `set_active_zone`, `zone_map`, `terrain_kinds`.
Rule lookups the screens read: `evolution_eligibility`, `interact_candidates_coded`,
`care_remaining_ms`. The tactical battle rules, wrapped for the client by
`client/src/tactics/wasm.ts`: `tactics_map`, `tactics_unit`, `tactics_targets`,
`tactics_path`, `tactics_disengage`, `tactics_flank`, `tactics_forecast`,
`tactics_recruit_odds`, `tactics_recruit_targets`, `tactics_ai_plan`, `tactics_plan`,
`tactics_overlays`, `tactics_tuning`, `tactics_deploy_slots`, `tactics_next_initiative`,
`tactics_fresh_budget`, `tactics_is_exhausted`. The golden harness entry the parity
tests call directly: `tactics_golden`. Constant accessors: `step_ms`, `move_queue_cap`,
`party_size`, `party_slot_none`, `talk_range`, `max_trade_monsters_per_side`,
`protocol_version`, `min_client_protocol`, `deletion_grace_ms_default` (returned as a JS `BigInt`). Values cross the boundary as
serde values (`serde-wasm-bindgen`). The
module parses zone maps once per instance and caches the active zone's tile map
until `set_active_zone` changes it. The parity evals (`prediction-parity`,
`movement-parity`, `js-path-parity`) run the native and wasm builds on the same
inputs and require identical output. `feature-isolation` checks that the client
crate never pulls in the server-only feature.

## server-module: the authority

### Layout

`server-module/src/lib.rs` wires the domain modules and holds the three lifecycle
reducers plus `sync_content`. Each domain module owns its reducers and the tables it
writes:

| Module | Reducers |
|---|---|
| `movement` | `join_game`, `enqueue_move`, `set_move`, `clear_queue`, scheduled `movement_tick` (the grass trigger opens a tactical wild battle through `tactics::start_wild_tactical`) |
| `battle` | no reducers since bt-17 (BT17.1): the 1v1 start and per-turn action reducers are deleted; the module keeps the write-back, terminal-sweep, faint-penalty and disconnect helpers the tactical settle funnel and the account lifecycle call |
| `taming` | dev-only `grant_bait`; the tactical recruit's insert (`insert_recruited`, called from `tactics.rs`'s recruit hook) — the 1v1 `attempt_recruit` is deleted since bt-17 |
| `tactics` | `deploy_units`, `submit_queue`, `cancel_queue`, `forfeit`, scheduled `tactical_deadline_fire`, `tactical_advance` and `battle_gc`; its two `pub(crate)` writers `start_wild_tactical` (called by `movement_tick`) and `start_pvp_tactical` (called by `accept_challenge`) are the only places a battle is created |
| `tactics_settle` | no reducers: the one terminal settlement `tactics::finish` calls (reward ledger, faint penalty, prior-terminal sweep, `battle_summary`) |
| `raising` | `care`, `train`, `essence_train`, `consume_crystalized_essence`, `heal_party` |
| `evolution` | `evolve`, `ack_evolution_notices` |
| `monster_mgmt` | `set_nickname`, `set_party_slot` |
| `economy` | `buy`, `sell` |
| `npc` | `talk`, `advance_dialogue`, `dismiss_dialogue` |
| `trading` | `cancel_trade`, scheduled `trade_offer_reaper`; `propose_trade`, `respond_trade` and `confirm_trade` are retired and return one fixed error |
| `trading_session` | `open_trade_session`, `set_trade_offer`, `confirm_trade_session`, `cancel_trade_session`, scheduled `trade_session_reaper` |
| `pvp` | `challenge_pvp`, `accept_challenge` (opens a tactical battle), `decline_challenge`, `cancel_challenge`, scheduled `battle_challenge_reaper` |
| `ranking` | `set_profile_name` |
| `accounts` | `start_guest_claim`, `complete_guest_claim`, `delete_account`, `cancel_account_deletion`, scheduled `guest_claim_reaper` and `account_deletion_reaper` |
| `access` | `set_world_access` (owner-only): the world's access rule (`Open`, `Password` or `Allowlist`) and the admission list; `require_admitted` (the access rule, then ownership) opens every non-owner-only client reducer but `unbind_world_account` and the account's own five, which open with `require_rule_admits`, the access rule alone |
| `world_binding` | `request_bind_nonce`, `bind_world_account` and their owner-relayed forms `request_bind_nonce_for`, `bind_world_account_for`; `unbind_world_account`, the one client reducer outside the owner-only set with no admission check, which erases the caller's `world_account` row with its armed re-check, its binding and its nonce, and withdraws its admission row when a `world_account` row went; owner-only `set_world_names`, `set_world_allowlist` (the list holds handles) and `drop_world_binding` (the same erasure for a named identity; does not write the list). Owns `world_binding`, `world_bind_nonce`, `world_name` and `world_allowlist`, and verifies the attestation (`verify_attestation`), whose binding grants nothing; a build with no attestation key refuses the four nonce and bind reducers; `delist_account_of`, the deletion cascade's step, takes a deleted identity's handle off the list |
| `account_checks` | procedures `check_account` (a client's one-use ticket), `check_account_for` (owner-only relay), scheduled `recheck_account` (the database only, armed by the connect reducer) and scheduled `host_account_check` (the database only: the account the world's host plays under): the world asks the account service the build names (`POST /world/check`, 3 s timeout) whether an account owns the game and stores the answer. Owns `world_account`, `world_check_budget`, `recheck_schedule`, `world_move`, `world_egress` and `host_check_schedule`; `entitled` and the `Allowlist` rule read `world_account` |
| `privacy` | `request_data_export`, scheduled `export_bundle_reaper` |
| `observability` | scheduled `mr_heartbeat` |
| `playtest` | scheduled `playtest_reaper` |
| `summary_reaper` | scheduled `battle_summary_reaper` (caps `battle_summary` at its newest 100,000 rows; armed by `tactics_settle`'s summary insert and by `init`/`sync_content`) |

Supporting modules have no reducers: `schema` (tables, views, the data-lifecycle
manifest), `guards` (shared validation), `marshal` (row ⇄ `game-core` conversion,
`now_ms`), `inventory` (the single `grant_item` insert path), `content`,
`content_cache` and `module_info` (`ensure_module_info`, the only writer of the `module_info`
row). Most checks more than one module needs are in `guards.rs`: `require_owner`,
`is_in_ongoing_battle`, `require_not_deleting` and the battle-input validators; the
admission check is `access::require_admitted`, and the item and currency headroom rules are
game-core's (`trading/rules.rs`). A module
writes another module's table only through a helper that module owns: `accounts::rekey_all`,
for example, calls each owner's `rekey_*` helper.

A reducer checks `ctx.sender()` and the request, calls `game-core`, and writes. It
returns `Err` to refuse, which rolls back the whole transaction, and logs the refusal
as a JSON line through `guards::log_reject`. Some of the refusals: an enqueue onto a full
move queue returns `Err("queue full")`; `guards::authorize_move` refuses an input seq at or
below `move_intent.last_input_seq`; `check_party_size` refuses an oversized party instead of
truncating it; `tactics::submit_queue` refuses an act for a unit that cannot act, a fainted
one included; and a purchase, a sale, a dialogue grant or a trade that would take the receiver
past `MAX_ITEM_STACK` or `MAX_BALANCE` is refused before anything moves (`check_item_headroom`,
`check_currency_headroom`, and `check_headroom` for a trade session). Scheduled reducers first check
`ctx.sender() == ctx.database_identity()`, so clients cannot call them.

### Lifecycle

- `init` (first publish only) records the publisher as `config.owner_identity`, seeds
  content, records the module's protocol numbers in the public `module_info` row,
  reconciles zone schedules (a new world has no player, so no zone is armed), arms the
  heartbeat, and arms each reaper that has something to reap (a new world has nothing,
  so the heartbeat is the only schedule).
- `sync_content` does the same reseed for the owner on later publishes, and brings the
  `module_info` row in line with the published module whether or not the content
  changed. It refuses other callers. `just publish` calls it after the publish, and every
  recipe and script that publishes over a database and keeps its data calls it as the
  publishing identity and fails when the call is refused.
- Protocol numbers. `PROTOCOL_VERSION` and `MIN_CLIENT_PROTOCOL` (never above it) are
  constants in `game-core/src/lib.rs`; `client-wasm` exports them as `protocol_version()` and
  `min_client_protocol()`, and `module_info::ensure_module_info` writes them into row 0 of
  `module_info` from `init` and `sync_content`. `client/src/net/wireContract.test.ts` holds the
  generated bindings against one recorded entry per protocol number in
  `client/src/net/wireContract.json`.
- `on_connect` first refuses an identity the world's access rule does not admit
  (`access::require_admitted_at_connect`), then records the connection in the private
  `player_session` table and, for
  a JWT from an allowed issuer, creates or updates the caller's `account` row.
  Connections without an account are accepted.
- `on_disconnect` deletes that connection's session row. If the identity has no
  other live connection, it resolves the identity's tactical battles (first — an
  Active wild battle auto-flees with its damaged HP persisted and its READY rows
  discarded, a Deploying one closes as `Fled` with nothing persisted, and the anchor
  stays terminal so the legacy wild resolver skips it), then its trade offers and trade sessions, PvP battles,
  legacy wild battles and challenges (`resolve_all_live_interactions`), then deletes
  the conversation, character and player rows. As it deletes the character it saves
  the character's zone, tile and facing in the private `last_position` table
  (`movement::save_last_position`).
- Schedules. In a world with nobody connected the schedules that keep running are the 60 s
  `mr_heartbeat`, which writes no row, and, once the owner has named the host's identity,
  the hourly `host_account_check` tick. Every reaper is a one-shot armed when something is
  owed. One that serves an entity (a trade offer, a challenge, an account deletion) has a
  row per entity at its deadline. `playtest_reaper` and `export_bundle_reaper` bound a table
  by age and have at most one row for the whole table, at the oldest row's expiry: the
  insert arms it, the reaper re-arms it from the rows it leaves, and an empty table has
  none. Each has a fixed delay (300 s and 3600 s), and a run arms its next run no sooner
  than that delay from now, so it runs at most once per delay; work owed at once (a table
  over its cap, a backlog one run could not finish) waits that delay too.
  `battle_summary_reaper` bounds its table by row count in the same shape (see "Schema and
  privacy model"). The runtime consumes a one-shot row even when its reducer's transaction
  fails, and the re-arm rolls back with that transaction, so a failed run leaves nothing
  armed until the next write to the table (a recruit attempt for `playtest_event`; an export
  request or a purge for `export_bundle`), `init` or `sync_content` re-arms it from the
  table's true oldest row. `docs/runbooks/observability-dr.md` says how to see that state.

### Movement

Movement is paced by the server, per zone. A client sends intent (`enqueue_move`,
`set_move`, `clear_queue`) tagged with a strictly increasing `seq`. The intent lives
in the private `move_intent` table, one row per player character keyed by
`character.entity_id`: the undrained queue
(capped at `MOVE_QUEUE_CAP`) and `last_input_seq`. `guards::authorize_move` rejects a
seq at or below that value, and the reducer then writes the queue and the new seq in
one `move_intent` update. An accepted input reads the caller's `player` row for its
entity id, reads no `character` row, and writes neither, so it changes nothing any
client subscribes to.

A zone has an interval schedule row that runs `movement_tick` every `STEP_MS` only
while a player's character is in it. `movement::arm_zone_tick` inserts the row when a
player enters (`join_game` for the zone it starts in, the tick's warp arm, and in the
load-test build `dev_place_in_load_zone`) and never adds a second row for a zone. The tick that finds no player's character in its zone puts each of the zone's
NPCs back on its home tile, Idle, writing only the rows that differ, and deletes the
zone's row, so leaving, warping out, disconnecting, timing out and account deletion all disarm the zone
through that one path and a world with nobody connected runs no `movement_tick`. An
NPC's facing is left as it was: it has no authored default. A
player in a battle is still in their zone. NPC wander reads a tick counter that is the
server clock divided by `STEP_MS`, not a count of ticks that ran, so a zone that
empties and is entered again continues from the clock. After a republish, zones that
still hold a row from before keep ticking if occupied and disarm on their next tick if
not.

A tick drains at most one move per character through `game_core::apply_move`, moves NPCs
with `npc_decide`, and rolls grass encounters. `apply_move` gives `MoveInput::Face` two arms: a
character that does not face the direction turns to it on the same tile, `Idle`, with
`move_started_at` stamped, and one that already faces it gets exactly the `Step` result, from the
match arm the two share. `Face` is the last `MoveInput` variant, after `Jump`; game-core's flat-code
helper `apply_move_coded` carries only `Step` and `Jump`, so `Face` crosses the wasm boundary on the
serde path. A move that lands on a warp tile moves the character to the warp's destination in the
same tick, `Idle` and with its queue cleared. The warp is skipped for a character whose player is in
an ongoing battle and for a mover with no player row (`skip_warp` defaults to `true`), and the NPC
wander step resolves no warp, so an NPC stays in its home zone. The tick is the only writer of
`character.move_queue` and `character.acked_seq` in every build but the load-test one, where
`dev_place_in_load_zone` also writes them as the warp arm does. The tick copies the private
queue and seq onto the character row (`movement::publish_intent`) in the same update that
carries the position, and writes the row only when something changed. The owner therefore
receives the acknowledgement and what is left of the queue together with the position,
up to one tick after the input was accepted, and every other client receives one
`character` update per step. A battle start empties each battler's private queue and keeps
its seq (`movement::drop_queued_moves`, from `tactics::start_wild_tactical` and
`tactics::start_pvp_tactical`), writing no public row; the next tick publishes the empty
queue. A character whose player is in a battle drains nothing, and `enqueue_move`/`set_move`
reject new moves during a battle. Quality-Time accrues in `enqueue_move`.

`join_game` puts the character where the account's last one stood: it consumes the
identity's `last_position` row (`movement::take_start`) and uses it when the saved zone
still has a map and the tile is walkable in it (`game_core::can_resume_at`), and
otherwise, or with no row, starts the character on the zone 0 spawn (`game_core::spawn`)
facing South; the row is consumed either way. It arms the zone the character starts in.
Nothing writes `last_position` while a character exists, so a step costs no extra write. A
disconnect while another connection of the identity is live saves nothing, and what a
battle, a trade or a conversation does on a disconnect moves no character: the position
saved after a wild battle's auto-flee is the grass tile, and after a PvP forfeit the tile
the character stood on. `last_position` is `Erase` in `DATA_LIFECYCLE_MANIFEST`: the
deletion cascade deletes the row (`movement::erase_last_position`), and during the grace
period `join_game` is refused before it reads the row, so a cancelled deletion resumes like
any other account. A guest claim re-keys the row onto the claiming account
(`movement::rekey_last_position`), and the row counts as game data for the claim's
destination-is-empty guard, so the claimed account's first join puts it where the guest
stood. `request_data_export` also accepts an account that has not
joined on any connection; that export omits the saved position, which the next export made
from inside the game carries in its `character` row.

`join_game` creates the `move_intent` row with the character; the last disconnect and
the account-deletion cascade delete it with the character. A character with no intent
row is an NPC. Should a player character ever lack one, the row is created from its
published queue and `character.acked_seq` (`movement::seed_intent`) by its first move
call or by the tick.

### Battles, trades and the rest

- **PvE.** A grass encounter opens a tactical wild battle
  (`tactics::start_wild_tactical`) and stores each wild's individuality seed
  in the private `battle_wild_unit` table; the battle's own seed lives in
  `battle_secret`. Turns resolve in `game-core`'s tactical engine from the stored
  seed. A recruit rebuilds the exact individual from the wild's seed at full HP,
  into the box (`taming::insert_recruited`, `PARTY_SLOT_NONE`); the recruited wild
  becomes `Recruited`, leaves the board and the initiative, and is never a `Ko`,
  so the settlement credits no XP for it. After a battle ends, only the latest
  finished battle per player is kept.
- **Reach.** The world's interaction target is one game-core rule, `game_core::interact_candidates`
  (exported to the client as `interact_candidates_coded`): the entities on `pos.step(facing)`, else
  on the character's own tile, same zone only, ordered NPC, heal, player, then id. The reducers
  check range more permissively. `talk` accepts `TALK_RANGE` (2) from the NPC's current tile.
  `open_trade_session` and `challenge_pvp` refuse a partner outside
  `game_core::interact::within_interact_range` (same zone, Manhattan distance at most
  `TALK_RANGE`), and `heal_party` refuses a caller outside that range of the heal location's tile.
  `buy` and `sell` refuse a caller outside `game_core::interact::within_npc_reach` of an NPC
  offering that shop (`sell`: any shop): the same zone and at most `TALK_RANGE + wander_radius`
  from the NPC's home tile. Each of those five has one message for every out-of-range case. In
  `challenge_pvp` the range check runs right after "target is joined and online" and before the
  checks that answer from the target's account, battles and pending challenges; in `buy`, `sell`
  and `heal_party` it runs after the deletion gate and before the battle guard and every read of
  the caller's wallet, inventory and cooldown. `accept_challenge` and `confirm_trade_session` check
  no range. `character`, `npc` and `heal_location_row` are public tables.
- **PvP.** The `battle` table is private; participants read it through
  `my_battle`. The battle checks are `guards::is_in_ongoing_battle` (the player,
  in either role) and `guards::reject_if_in_battle` (the monster, in either party),
  which `evolve` and the trade-session side check use. Challenges are public rows
  with a 120 s TTL (`CHALLENGE_TTL_MS`). Accepting one opens a tactical battle
  (`tactics::start_pvp_tactical`) whose deploy picks are revealed by copy; the tactical
  clocks and auto-pass rules end a stalled battle. Only a battle between two distinct
  real players is ranked (`guards::is_ranked_pvp`): Elo from `INITIAL_RATING` 1000,
  with no floor. Ranked results update the public `profile` table, and `ranking.rs` then
  rescans it into `leaderboard_top`, the identities of the top 100.
- **Trading.** Trades run through trade sessions (next item). The public `trade_offer`
  table is drain-only: no reducer inserts a row. A row still in it keeps its
  assets guarded (they cannot be spent, sold or evolved) until `cancel_trade`,
  a disconnect, account deletion or the one-hour TTL reaper (`TRADE_OFFER_TTL_MS`)
  deletes it. `propose_trade`, `respond_trade` and `confirm_trade` pass the admission
  check and return one fixed error. The client neither subscribes to the table nor sends
  `cancel_trade`: the disconnect sweep and the reaper are a remaining row's way out.
- **Trade sessions.** `open_trade_session` opens a blank private `trade_session` row with
  a player within interact range (one per pair, at most four opened per player, one-hour
  TTL). Each side replaces only its own offer with `set_trade_offer`; every accepted
  edit advances the row's revision and clears both confirms. `confirm_trade_session`
  names the revision it reviewed; the confirm that completes the pair re-checks both
  sides on live rows and executes the swap in the same call (monsters arrive in the
  receiver's lowest free party slots, then Storage). A side's assets are locked only
  while that side is confirmed; an offered monster that is boxed, faints or changes owner
  deletes the session at the monster write (`monster_mgmt::update_monster_synced`),
  and so do a disconnect and a cancel. The two participants read the row through
  `my_trade_session`; the client does not subscribe to it. The open cap is
  `MAX_OPEN_TRADE_SESSIONS` and counts only the sessions the player opened
  (`check_session_open`, `game-core/src/trading/session.rs`). A confirm runs
  `side_check` (eligibility, receipt headroom, both offers non-empty, the side
  keeps a monster) and first compares each offered monster with its private
  `trade_session_snapshot` row; arrivals take `arrival_slots`. The swap is
  `trading_session::apply_swap`, called when the last confirm lands. It resets
  each transferred monster's seven bond columns (`trust_favorable_count`,
  `trust_unfavorable_count`, `trust_favorable_battle_day_epoch`,
  `quality_time_ticks_total`, `quality_time_accum_ms`, `quality_time_window_ms`,
  `quality_time_window_start_ms`) through game-core's `reset_bond_on_trade` over a
  `TrainerBond` (`raising/rules.rs`), then rewrites `monster_pub` with the trust and
  Quality-Time tiers re-derived and the evolution `tier` copied forward. The guest-claim
  re-key (`monster_mgmt::rekey_monsters`) does not reset the bond.
- **Raising and economy.** Care, training, essence and healing live in `raising`;
  every payment and charge goes through `economy::grant_currency`/`spend_currency`
  (the guest-claim re-key, `economy::rekey_wallet`, and account erasure write the
  wallet row directly), and every inventory insert through `inventory::grant_item`,
  which keeps one stack per owner and item. The wallet is the private
  `player_wallet` (`u64`, `MAX_BALANCE` in `game-core/src/currency.rs`); a
  stack caps at `MAX_ITEM_STACK` (`trading/rules.rs`), and a swap applies its
  debits before its credits (`SwapPlan::ordered_steps`). The escrow wrappers in
  `guards.rs` count a confirmed session side and any `trade_offer` row still in its
  table. The client keeps currency a `bigint` from the store row to the reducer
  argument (`client/src/ui/tradeSessionModel.ts`). `heal_party` (`raising.rs`)
  charges a heal location's `cost_currency` and its cost item; the shipped
  `game-core/content/heal_locations/` name neither. Each credited knockout of a wild
  pays `battle_currency_reward` (`BATTLE_CURRENCY_BST_DIVISOR`, `currency.rs`);
  the one shipped quest's `reward.currency` (`game-core/content/quests/`)
  is credited once. A wild pack is clamped to the party's conscious monsters
  (`effective_pack`, `tactics/encounter.rs`). `docs/economy-tuning.md`
  is the worksheet, and `game-core/tests/pt_d3_tuning.rs` holds
  its relations as tests over the shipped content, among them
  `recruit_heavy_zone0_battles_buy_a_lure_berry_within_the_battle_budget`.
- **Evolution.** Edges are authored in `game-core/content/evolution_paths/*.ron`
  and seeded into the public `evolution_path` table. The content lints hold each
  `edge_id` unique (R12) and each edge's tier step at exactly one (R5). Eligibility is
  `game_core::eligible_evolution_paths`. After a write that can change eligibility,
  `check_and_evolve` (`evolution.rs`) re-reads the monster, applies the one eligible
  edge when there is exactly one, and repeats against the new species, at most
  `MAX_EVOLUTION_CHAIN_STEPS` times. The `evolve` reducer takes the one edge matching
  both endpoints, then calls `check_and_evolve`. Each applied evolution appends
  a reveal to the owner's private `pending_evolution_notice` row, read through
  `my_pending_evolution_notices`; `ack_evolution_notices` drains an acknowledged
  prefix. See the evolution entry in `docs/DECISIONS.md`.

### Dev and load-test builds

- **Features** (`server-module/Cargo.toml`). `dev_reducers` compiles `grant_bait`

### Private worlds

A single-player or friends world checks its players' accounts itself, applies its host's access rule
and, on a build that enforces ownership, refuses a caller whose account does not own the game. The
reasons are in `docs/DECISIONS.md`, from "A private world checks an account itself…" to "Ownership
is enforced unless a dev feature switches it off".

**Account checks.** In a single-player or friends world the player connects under that world's own
anonymous token and never sends an account token. The world asks our account service itself whether
the player's account owns the game, through four procedures in
`server-module/src/account_checks.rs`, and keeps the answer in private `world_account {handle,
identity, entitled, checked_at_ms, is_host}`, which an identity reads through `my_world_account`
(its own row alone). A handle is what the service answers for one account in one world: opaque, the
same at every check, and not a credential.

- **First contact.** A client whose identity the world does not know asks the account service's
  `POST /ticket` for a one-use ticket naming the world as its own software authenticated it, and
  calls `check_account(ticket)`. The procedure refuses a ticket that is not 43 base64url characters,
  a world that presents no name (see The world's address below), and a caller once the world has
  sent 30 ticket redeems in the current minute (the one row of `world_check_budget`); none of the
  three sends anything. Otherwise it presents the ticket, the names the world presents and its
  database identity at `POST /world/check` under a 3 s timeout, and stores the answered handle and
  entitlement, a negative answer included, in one transaction; `Ok` carries whether the account owns
  the game. A `403` (`the account service refused the ticket`) and any other failure, a timeout
  included (`the account service gave no answer`), refuse the call and change no `world_account`
  row. An identity the access rule has not admitted cannot connect, so the world's owner relays its
  ticket through `check_account_for(who, ticket)`; the relay counts in the budget and is never
  refused by it. A handle another identity holds moves that identity's character to the caller
  (`docs/DECISIONS.md`, "One character per account in a world: a check under a handle another
  identity holds moves the character"). A second account for an identity that holds one is refused
  (it unbinds first).
- **Each later connection.** The connect reducer arms one one-shot `recheck_schedule` row for an
  identity whose row was last checked 10 minutes ago or more, that has none armed and whose account
  is not pending deletion, and stamps the row's `checked_at_ms` as it arms: the world asks about one
  identity at most once in 10 minutes, however often it connects and whatever the run does.
  `checked_at_ms` is therefore when the world last asked, not when it was last answered. The host
  runs `recheck_account` from it (any other caller is refused before anything is sent), which
  presents the stored handle and stores the answer: a handle the service does not know is stored as
  not entitled; a handle under the service's newer key takes the stored one's place in
  `world_account` and in `world_allowlist` in the same transaction; a newer handle another identity
  already holds leaves the row's handle and stores the standing on it. The connection is admitted
  and entitled by the stored row the whole time, and a row never expires. A run with no answer
  leaves whether the account owns the game unchanged, the host spends the one-shot row whatever the
  run did, and the first connection 10 minutes after the arming asks again.
- **The host's own check.** The owner names the identity the host plays as with
  `set_host_identity(who)`: it marks that identity's row (`is_host`), clears the mark on every other
  row and arms one row of private `host_check_schedule {scheduled_id, scheduled_at,
  last_success_ms}`, which ticks `host_account_check` every hour. Refused with no write: a caller
  that is not the owner, an identity whose account is pending deletion, a build that names no
  account service, and an identity that holds no row (`that identity holds no account here`). A tick
  asks about the marked row's handle, and no other, when the schedule row holds no success, one 23
  hours old or more, or one stamped after the tick's own time; otherwise, and while no row is marked
  or the marked account is pending deletion, it sends nothing. Any caller but the database is
  refused before anything is read. The answer is stored as a re-check stores it, and the success is
  stamped only when the answer landed on the row asked about, still marked, the schedule row still
  holds what the tick read, and the world still asks over the address family the request went over.
  An answer about an account that entered deletion during the wait stores its address alone. A tick
  that gets no answer writes nothing, so the next one asks again. Naming another identity, and a
  `set_world_names` call that changes the set of names, leave the schedule row with no success, so
  the next tick asks. The schedule row is never updated: every change deletes it and inserts
  another. The mark stays on its row through a newer handle and a move, until another identity is
  named or the row is erased.
- **The world's address.** Every answer reports the address the service saw the request leave from,
  and the world stores it in private `world_egress {family, address, confirmed_at_ms}`, one row for
  IPv4 and one for IPv6. A re-check and the host's check store it in the transaction that stores
  their answer. A redeem stores it in a transaction of its own, before the one that stores the
  account, so a redeem that is then refused has still stored it. The world sends every request to
  the service's check name for the address family of its `ip:` names, `ipv4.` or `ipv6.` in front of
  the host its profile names (IPv4 when it lists `ip:` names of both), so the address reported is of
  that family. A redeem presents a `spki:` or `dns:` name always, and an `ip:` name only when it
  carries an address of that family and either no address is stored for the family or the stored one
  is the name's own and was confirmed under 25 hours ago. A world that presents no name is refused
  before anything is sent (`this world has no name to check an account under`). The answered name
  must be one the world presents when the answer lands, that answer's own address counted, or the
  redeem is refused (`the account service refused the ticket`). Addresses are compared as addresses,
  an IPv4-mapped IPv6 address as the IPv4 address it carries, and a row stamped after the
  transaction's own time vouches for nothing.
- **Deciding after a wait.** Other transactions run while a request waits, and a transaction's body
  may run twice. The transaction that stores an answer reads again every row it decides on (the
  admission or the ownership, the deletion state, the world's names, who holds the handle), and a
  re-check leaves alone a row that was unbound, checked again or replaced meanwhile, so an older
  answer never overwrites a newer one. A refusal is logged once, outside any transaction. No log
  line, table or return value holds a ticket, and no log line or return value holds a handle.
- **What reads the row.** `accounts::entitled` (`docs/DECISIONS.md`, "Ownership is enforced unless a
  dev feature switches it off") and, under `Allowlist`, `access::is_admitted`, which admits an
  identity that holds a row exactly while its handle is on the host's list (`docs/DECISIONS.md`, "A
  world that is not open refuses an unadmitted identity at connect and in every reducer; the owner
  relays the door").
- **Erasing it.** `unbind_world_account()` erases the caller's row with its armed re-check, and the
  owner's `drop_world_binding(identity)` does the same for a named identity. The unbind is the one
  reducer of the client roster the access rule does not gate, so a player whose handle the host took
  off the list can still erase the link, over a connection the connect reducer let in while the
  player was admitted. When a row goes, that identity's `world_admission` row goes with it, under
  every rule. A caller with nothing to erase gets `Ok` with no write (the drop answers `that
  identity holds no world binding`), and an account pending deletion is refused by the deletion
  gate. The deletion cascade takes the identity's handle off the host's list and erases the row and
  the identity's `world_move` row; a guest claim erases both for the guest identity it retires and
  moves none; the data export carries the caller's own row of each.
- **The client's half.** A connection to a `local` or `private` target subscribes `my_world_account`
  and `my_world_move` and reads its own rows at each applied snapshot, before any join
  (`client/src/net/worldTicket.ts`, `client/src/net/connection.ts`). A move row sends nothing and
  the page says the character is playing on another client; an own account row joins with no request
  to the account service; with neither row and a ticket source it asks for a ticket for the world's
  name (`worldNameFor`), calls `check_account(ticket)` on the raw connection, and joins only if the
  world answered that the account owns the game; with no source, or a build that checks no account,
  it joins as before. Only the page's first such snapshot runs first contact by itself; a later one
  waits for the player (`Connection.checkIn()`), because an account gets ten tickets a minute across
  every world and a host that drops the link could otherwise draw one per reconnect. A ticket source
  is one interface, `TicketSource { ticket(world), signIn() }`; the one built,
  `createIdTokenTicketSource`, is a page that signs in to the account service itself and holds the
  ID token in memory, and `main.ts` builds it only for a `local` or `private` target outside the
  desktop shell when `VITE_MR_WORLD_TICKET_ISSUER` is set. The gate is the menu frame's gate mode,
  the frame the sign-in gate of a server we operate uses (`worldGateStep`, `buildWorldGateView`).
- **Which service.** `BuildProfile::world_check_url` (`docs/DECISIONS.md`, "The official build holds
  no attestation key and a world build trusts no login issuer").
- **What keeps the surface closed.** `findDefinitionViolations`
  (`scripts/verify-release-reducers.mjs`) refuses a module definition that declares any procedure
  but these four, or any schedule but the module's own, on the default build and on each release
  artefact. The reducer census (`server-module/src/privacy_enforcement_tests.rs`) refuses a
  `procedure` attribute outside `account_checks.rs` and pins the tables each procedure reaches: for
  the two first-contact procedures `world_account`, `world_check_budget`, `world_allowlist`,
  `world_move`, `recheck_schedule`, `world_egress` and the tables a character move writes;
  `world_account`, `world_allowlist` and `world_egress` for the re-check; those three and
  `host_check_schedule` for the host's check. The same file proves `world_egress` and
  `host_check_schedule` private, with no view over either. The client's procedure surface is pinned
  by `evals/client-surface-privacy.eval.mjs`, and the wire contract records each procedure's
  arguments and return type.

The attestation binding is compiled beside it (`server-module/src/world_binding.rs`: the tables
`world_binding` and `world_bind_nonce`, their two views, the four nonce and bind reducers and the
verifier). It records a binding that nothing reads: it entitles and admits nobody, and it is to be
removed with `POST /attest`. A caller who is not entitled is refused by every reducer a player plays
through (`docs/DECISIONS.md`, "Ownership is enforced unless a dev feature switches it off"). Proved
by `server-module/src/account_checks_tests.rs` and, for the host's own check,
`server-module/src/account_checks_host_tests.rs` on the native test host, with every answer of the
service stubbed. That host runs a scheduled procedure as the scheduler would call it and runs no
scheduler, so the hourly tick and a request to a check name are not measured on a published module.
The measurements on 2.16.1, the four alternatives with a judge's scores and the slice changes are in
`docs/refactors/account-checks.md`.

**A character move.** When `check_account` or the owner's `check_account_for` is answered with a
handle that another identity of the world holds, the two identities are one account at two clients,
and the transaction that stores the answer moves the character to the identity the ticket was
redeemed for. `accounts::move_character` carries every row that makes up the character: monsters and
their public twins, pending evolution notices, inventory, quests and the whole dialogue row, the
heal cooldown, the wallet, the ladder profile with its name, the formation, the handle with its
discriminator, and the position. It deletes the challenges that name the source and the source's
export bundles. The handle's `world_account` row then points at the new identity and keeps its host
mark, the source's armed re-check is deleted, and private `world_move {identity, moved_at_ms}`
records the identity the character left, which reads its own row through `my_world_move`. That
identity's next successful check deletes the row, and until then `join_game` and
`complete_guest_claim` refuse it (`this character is playing on another client; sign in again to
play here`), so checking in again with the same account moves the character back.

- **Position.** A source that is in the game has its character's zone, tile and facing saved as the
  destination's `last_position`, and its `character`, `move_intent` and `player` rows are deleted,
  the `player` row last. The destination's own `join_game` makes its character there. The source's
  later disconnect finds no `player` row and writes nothing of the character.
- **Refusals, each with no write.** A ticket whose answered name is neither a `spki:` name, a `dns:`
  name nor an `ip:` name the world has confirmed (`this account already plays here under another
  identity`); a caller that holds another account; a caller that owns a character (`this identity
  already plays a character here`); and, under one reason (`this character cannot change clients
  right now`), either identity in an ongoing battle or named by a trade offer or session, or a
  source whose account is pending deletion. The world has confirmed an `ip:` name while the address
  stored for its family in `world_egress` is the name's own and was confirmed under 25 hours ago,
  read after the answer's own address is stored (`docs/DECISIONS.md`, "A private world checks an
  account itself: a one-use ticket at first contact, then the account's handle").
- **What stays under the source.** Its `world_move` row; finished battles and what records them
  (`battle`, `battle_summary`, the tactical rows until their sweep, `playtest_event`); and the rows
  about that identity's own connection, admission and login (`player_session`, `world_admission`,
  `world_admission_attempt`, `world_binding`, `world_bind_nonce`, `account`).
- **Admission.** A move admits nobody. The source's `world_admission` row is deleted when the access
  rule was not admitting the source before the move, which is a source under `Allowlist` whose
  handle is off the host's list, and is kept otherwise, so the first client can connect, read its
  `world_move` row and check in again. Under `Allowlist` a source with no admission row is refused
  at connect once its account row is gone, and comes back through the owner's relay.
- **Deletion and export.** The deletion cascade and a guest claim, for the guest identity it
  retires, delete an identity's `world_move` row (`account_checks::erase_world_move`), and the data
  export carries the caller's own. An unbind and the owner's drop leave it: the row goes only by a
  check, the identity's own or one the owner relays, or by the cascade.

Proved by `server-module/src/account_checks_tests.rs` (`mod character_move`, and `mod ip_move` for a
move through an `ip:` name) through the procedures with the service's answer stubbed, and by the
tests of `accounts::move_character`, `movement::move_position` and `ranking::move_profile`.
`docs/local-play.md` ("One character per account: what a move carries and what it costs") holds the
measured cost.

**The attestation check.** `world_binding::verify_attestation(keys, attestation)` runs these checks
in order: a token over 4096 bytes is refused before anything is decoded; three non-empty segments of
strict unpadded base64url (`base64` 0.21); a header that is a JSON object, of which only `kid` is
read (`alg` never is); the key from the build's own `kid`-keyed list, never from the token; a
64-byte signature that `verify_strict` accepts over `<header>.<payload>`. The payload is parsed only
after the signature verifies (`serde` derive over `serde_json`): string `sub`, `aud` and `nonce`,
integer `exp`, optional `mr_ent` array of strings, a repeated or wrongly typed member refused, `sub`
1 to 255 visible ASCII. `iss`, `iat` and `jti` are not read.

**World names.** A browser page's names for a ticket are computed by `worldNameFor` in
`client/src/net/worldTicket.ts`. A world holds its own names in a private table its owner writes
with `set_world_names` (at most 16, each 1 to 512 visible ASCII characters; a world with no name
accepts no binding), and `bind_world_account` accepts an attestation only when its `aud` equals one
of them, byte for byte. The module's half is proved by `mod bind_refuses` and `mod relay_rig` in
`server-module/src/world_binding_tests.rs`.

**Build profiles.** A release build of the module is one of two. The `official` build trusts the
production login issuer and holds no attestation key. The `world` build, which the desktop shell and
the standalone server ship, holds the production attestation keys and trusts no login issuer. Both
lists are constants of the build: `BuildProfile::attestation_keys` is empty on `official`, `default`
and `conflict`, `PRODUCTION_ATTESTATION_KEYS` on `world` (empty, since no production key is
published, so a `world` build binds nothing and entitles nobody) and `DEV_ATTESTATION_KEYS` (the
published `local-dev` key; `hosted-dev` publishes none) on `test` and `dev-enforcing`; a test holds
the lists to the generated `account-service/attestation-public-keys.json`. On a build with no key
the six binding reducers (`bind_world_account`, `request_bind_nonce`, the owner-relayed form of
each, `unbind_world_account` and `drop_world_binding`) return `this server takes no world binding`
as their first statement, before anything is decoded, read or written; the unbind and the drop do so
only on a build that also names no account service to ask. A binding records the `kid` that signed
it, and no rule reads a binding on any build. On the `world` build every token is an anonymous
guest's. The two builds have one schema and one set of client bindings. The builds also differ by
the account service a world asks about an account (`BuildProfile::world_check_url`, the `POST
/world/check` address). `official`, `default` and `conflict` name none: each of the four
account-check procedures answers `this server checks no account` as its first statement, and
`entitled(ctx, profile)` reads no `world_account` row there, so the official build has the login
token as its one way in. `world` names the production service, a placeholder under a reserved name
that answers nothing, so a `world` build entitles nobody until a real address ships. `test` and
`dev-enforcing` name `hosted-dev`, because the host refuses a procedure's request to `local-dev` on
loopback (`docs/refactors/account-checks.md`, row P2). The artefact's `mr_build_profile` section
does not carry the address. Proved by `mod binding_build` and `mod official_build` in
`server-module/src/world_binding_tests.rs` (the second under the `official` build, which no run of
`just ci` includes: `cargo nextest run --workspace --no-default-features --features
monster-realm-module/official -E 'package(monster-realm-module) & test(/official_build/)'`).
`docs/local-play.md` §3, fork (b).

**Access.** While a world's access rule is `Password` or `Allowlist`, the connect reducer refuses,
as its first statement, an identity that `access::is_admitted` does not admit
(`access::require_admitted_at_connect`), and every reducer of the generated client roster that is
not owner-only makes that admission check, except `unbind_world_account`, which makes none
(`docs/DECISIONS.md`, "A private world checks an account itself: a one-use ticket at first contact,
then the account's handle"). The five reducers an account reaches whatever it owns make it through
`access::require_rule_admits`, the access rule alone; the others make it through
`access::require_admitted`, which makes it and then the ownership check (`docs/DECISIONS.md`,
"Ownership is enforced unless a dev feature switches it off", which names the five). The owner-only
ones are `sync_content`, `set_world_access`, `set_world_names`, `set_world_allowlist`,
`set_host_identity`, `drop_world_binding` and the two relayed binding reducers. The binding reducers
answer their build's refusal before that check; it reads nothing. The procedure `check_account`
makes the admission check before it sends anything and again before it stores an answer, and
`check_account_for` the owner check. A world with no `world_access` row is `Open`. Under `Password`,
`is_admitted` admits the owner and an identity in `world_admission`. Under `Allowlist` it admits the
owner; an identity that holds a `world_account` row exactly while that row's handle is a row of
private `world_allowlist` (at most 256 handles of 1 to 1024 visible ASCII, in the column named
`account_subject`), and nothing else counts for it, so delisting refuses at the next check; and an
identity with no such row only when it holds a `world_admission` row. An attestation binding is not
read. The list is read at every check and nothing is stored from it. When the rule changes to one
that is not `Open`, `set_world_access` gives an admission row to each live identity that the rule in
force before the call admitted, and to none that rule refused. A new joiner's way in under
`Allowlist` is the owner's relayed account check (`check_account_for`) and the listing of the handle
it stored. Admission rows are written only by the owner-only reducer `set_world_access`, which takes
the joiners' identities, and deleted by a player's own unbind and the owner's `drop_world_binding`
when either erases a `world_account` row, and by the deletion cascade and a guest claim (for the
retired guest). A retired guest identity that reconnects holds no world row: in a `Password` or
`Allowlist` world it is refused until the owner admits it or relays a check for it.

The list is the owner's to edit (`set_world_allowlist` replaces it) and is made from the players
already let in. When the rule changes to `Allowlist`, `set_world_access` adds the handle of every
`world_account` row whose identity the rule in force before the call admitted (under `Open` every
one; under `Password` those holding a `world_admission` row, and the owner's), beside the handles
already listed; its `admit` argument adds none. While the rule is `Allowlist`, the handle of the
owner identity's own row stays listed: `set_world_allowlist` stores it whether or not the call names
it, and a check of the owner's identity adds it. The list never passes 256 handles: a rule change
that would add past that, a `set_world_allowlist` that would store the owner's handle beside 256
others, and an owner's check under `Allowlist` of a handle a full list lacks are each refused with
the list's too-many error and no write. Under `Open` and `Password` the list is kept, stored as the
owner names it, and not read; the next change to `Allowlist` adds to it. A re-check that the service
answers under a newer handle puts that handle in the listed one's place. An account's deletion takes
the handle of the deleted identity's `world_account` row off the list; an identity with no row takes
nothing off, and a row the host typed that equals the handle goes too, because it names the same
account (`world_binding::delist_account_of`, called by `accounts::account_deletion_reaper` before
the row's erase). The row is the only record of the handle, so an identity whose row is already gone
takes nothing off: a player who unbinds, or whose row the owner drops, before the account's deletion
leaves the handle listed. A guest claim does not write the list either, so the handle of the guest
identity it retires stays listed until the host removes it.

The module declares no HTTP handler, no HTTP route and no row filter: a check of the generated
module definition refuses each, on the default build (`just module-definition`, in `just ci`) and on
each artefact `just release-module` makes (`scripts/verify-release-reducers.mjs`, over
`spacetimedb-standalone extract-schema`). All three sit behind the `spacetimedb` crate's `unstable`
feature, which the workspace enables, so that check is what keeps them out (`docs/DECISIONS.md`,
"The crate's `unstable` feature is on; the generated definition is checked instead"). The same check
and the deletion-gate census allow the four account-check procedures and no other. Built: the
module's half (`server-module/src/access.rs`, and the list in `server-module/src/world_binding.rs`);
`mod admission_roster` in `server-module/src/privacy_enforcement_tests.rs` takes the reducer roster
from the generated bindings' file names and executes every shipped reducer as an unadmitted caller
on a `Password` world. Designed, not built: the gate's half (the door endpoint and its password
check, closing a removed identity's sockets), in `docs/local-play.md` §3, fork (a); see
`docs/DECISIONS.md`, "The gate checks a world's password; the module never receives one".

**Reducer arguments.** `set_world_access(rule, admit)` is owner-only and stores the rule and nothing
else: `world_access` has no salt or hash column. `mod reducer_arguments` in
`server-module/src/privacy_enforcement_tests.rs` describes every reducer the build declares, the dev
builds' listed by hand, and holds that no argument is named for a password and that the arguments
carrying text are a reviewed roster.

**The ownership gate.** On an enforcing build the gate `access::require_admitted`, which every
reducer a player plays through opens with, makes the ownership check straight after the access rule
and before the reducer reads or writes anything else (`accounts::require_entitled` under
`BUILD_PROFILE`). The caller's connection must carry a token from one of the build's login issuers,
addressed to `ALLOWED_AUDIENCE`, whose `mr_ent` claim names `base-game`, or the caller's
`world_account` row must say its account owns the game, as below (an attestation binding entitles
nobody). Anyone else, an anonymous connection included, gets the one fixed error `ownership
required`, and nothing is written; this holds whether or not the identity has joined. An identity
the access rule does not admit gets the admission refusal first, and nothing of ownership is read. A
build that does not enforce admits everyone and never reads the token. The claim is read by a small
scanner over the token's raw payload, since the module has no JSON crate
(`token_names_entitlement`): exactly one top-level `mr_ent`, an array holding the string; a
duplicate key, an escaped key or text the scanner cannot follow fails closed.

The 51 reducers of the generated client roster split four ways. 37 are gated, `join_game` among them
and reducers that need no `player` row, such as `care`, `train`, `evolve`, `set_nickname` and
`set_party_slot`; the two player binding reducers answer their build's refusal (`this server takes
no world binding`) before the gate. 5 are the account's own and open with
`access::require_rule_admits`, the access rule alone: `delete_account`, `cancel_account_deletion`,
`request_data_export`, `start_guest_claim` and `complete_guest_claim`. 8 are owner-only and make
their owner check and no ownership check (named in "A world that is not open refuses an unadmitted
identity at connect and in every reducer; the owner relays the door"). `unbind_world_account` makes
neither the admission check nor the ownership check. The connect reducer and the four account-check
procedures of `server-module/src/account_checks.rs` ask nothing about ownership: where a world
checks accounts itself, an identity becomes entitled by connecting and checking its account in.

The gate reads what is stored when the call runs: the token the connection opened with and the
caller's `world_account` row. It asks the account service nothing. So an identity that has joined is
refused from the first call that finds it not entitled: after a re-check or the host's own check
stores a negative answer, after the owner drops its row (`drop_world_binding`), after it unbinds, or
after its character moved to another identity (the row then points at that identity).

`accounts::entitled(ctx, profile)` entitles everyone on a build that does not enforce. An enforcing
build entitles a connection whose login token entitles it, or whose identity holds a `world_account`
row that says its account owns the game, however long ago the account service said so
(`docs/DECISIONS.md`, "A private world checks an account itself: a one-use ticket at first contact,
then the account's handle"). `require_entitled` writes nothing, and reads `world_account` only when
the token does not entitle and the profile names an account service. So on a dev-enforcing build a
connection with no row, one whose row says the account does not own the game and one that holds only
an attestation binding are all refused by `join_game` with `ownership required`, under `Open`,
`Password` and `Allowlist` (`mod acs6_enforcing_bound` in
`server-module/src/world_binding_tests.rs`; `mod open_join_unbound` holds an unbound join accepted
under `open_join`). Every other gated reducer refuses them the same way.

### Working with SpacetimeDB

- **Lockstep.** The spacetime CLI and host, the Rust crate and the npm SDK are one version: the
  root `Cargo.toml` (`=2.16.1`), `SPACETIME_VERSION` in `scripts/ci-tools.sh`, and
  `client/package.json` (`^2.16.1`, locked in `client/package-lock.json`).
  `scripts/ci-tools.test.mjs` holds the resolved crates (`cargo metadata`), the locked npm SDK
  and the generated bindings to one version; `bindings-drift` holds the bindings to the CLI on
  PATH, which CI installs from `SPACETIME_VERSION`. Upgrades follow
  `docs/runbooks/spacetimedb-upgrade.md`. The nightly `smoke-republish` job republishes over
  live data without `--delete-data` and checks that the data survives.

- Syntax is 2.x: `#[spacetimedb::table(accessor = x)]`, `ctx.sender()`,
  `ctx.database_identity()`. `.claude/skills/spacetimedb-reducer` has the details.
- `#[table(accessor = x)]` generates a crate-private trait `x`; a module that uses
  `ctx.db.x()` for a table declared in another module has to import that trait
  (for example `use crate::schema::config;`). `cargo check` reports a missing import.
- A scheduled table has to be declared in the same module as its reducer so the
  `scheduled(reducer)` attribute resolves; that is why the reaper schedule tables live
  next to their reducers instead of in `schema.rs`.
- Time columns are `i64` milliseconds: `marshal::now_ms` converts
  `ctx.timestamp.to_micros_since_unix_epoch()`.
- A one-shot `spacetime call` opens its own connection and closes it afterwards, so
  it runs `on_connect`/`on_disconnect` around the reducer. A presence row created by
  such a call is deleted when it returns.
- Subscribing to a private table from the client fails the whole subscription batch.
  Clients subscribe to the owner-scoped view instead.
- Schema changes on a live database must be additive between consolidations
  (append columns with a `#[default]`); see `docs/DECISIONS.md`. An `i64` default is typed
  (`#[default(0i64)]`): an untyped `0` encodes as 4 bytes and the publish fails.

## Schema and privacy model

All tables are declared in `server-module/src/schema.rs`, except the scheduled tables
(which live with their reducers) and `playtest_event` (`playtest.rs`). Visibility is
part of the schema:

| Class | Tables | Client read path |
|---|---|---|
| Public content | `species_row`, `skill_row`, `item_row`, `type_relation_row`, `zone_def`, `shop_row`, `shop_item_row`, `heal_location_row`, `npc`, `evolution_path`, `config` | direct subscription |
| Public world state | `character`, `player`, `profile`, `leaderboard_top`, `battle_challenge` | direct subscription; `character` only for the own row and per zone (see "Connection and store"); `profile` only for the `leaderboard_top` members (a join) and the own row |
| Public, drain-only | `trade_offer` | none in the client: no query subscribes to it and the store holds no offer state |
| Private, owner-readable | `monster_pub`, `inventory`, `player_quest`, `player_wallet`, `player_conversation`, `account`, `pending_evolution_notice`, `export_bundle`, `world_binding`, `world_bind_nonce`, `world_account` | views `my_monster_pub`, `my_inventory`, `my_player_quest`, `my_wallet`, `my_conversation`, `my_account`, `my_pending_evolution_notices`, `my_export_bundle`, `my_world_binding`, `my_bind_nonce`, `my_world_account` |
| Private, owner-readable (tactical) | `battle_queue`, `battle_deploy`, `player_formation` | views `my_battle_queue`, `my_battle_deploy`, `my_formation` |
| Private, participant-readable | `battle`, `battle_tactical`, `battle_unit`, `battle_event`, `battle_clock`, `trade_session` | views `my_battle`, `my_tactical_battle`, `my_battle_units`, `my_battle_events`, `my_battle_clock` (either side, joined through `battle`), `my_trade_session` (opener or partner) |
| Private, server only | `monster`, `encounter`, `battle_secret`, `battle_wild_unit`, `battle_summary`, `trade_session_snapshot`, `player_dialogue_state`, `heal_cooldown`, `last_position`, `guest_claim`, `player_session`, `world_access`, `world_admission`, `world_admission_attempt`, `world_name`, `world_allowlist`, all schedule tables | none |

A view takes only its context and filters on `ctx.sender()` through an index. That
body is the whole security boundary.

- **The party index.** The private `monster` table has two indexes over its owner
  (`server-module/src/schema.rs`). The single-column `owner_identity` serves reads that need every
  monster an owner holds: re-key, erase, export and `has_monsters`. `owner_party` is a btree over
  `(owner_identity, party_slot)`. Every party read on a per-input or per-tick path goes through its
  `(owner, 0..PARTY_SLOT_NONE)` range, which yields the party in slot order. Those reads are
  `battle::lead_party_ids` (every accepted `enqueue_move`, the tick's band check, the tactical
  start, `refresh_lead_level`) and `monster_mgmt::set_party_slot`'s occupied-slot read;
  `raising::heal_party`, once per heal, still filters `owner_identity`. A compile-time assert in
  `battle.rs` pins `PARTY_SLOT_NONE == u8::MAX`, because only then does the range mean "not in
  Storage".
- **`monster` vs `monster_pub`.** `monster` holds the hidden genes (IVs, EVs, nature)
  and server-side counters. `monster_pub` is the safe projection (derived stats, HP,
  party slot, tiers, essence). The server writes both together; the owner reads
  `monster_pub` through `my_monster_pub`. Other players' monsters are not delivered
  at all.
- **`inventory`.** Item counts are private because scouting another player's stock is
  a competitive leak. `my_inventory` returns only the caller's stacks. Reducers read
  the table directly.
- **`battle`.** Only the two participants see a battle, through `my_battle`. A
  practice battle (same identity on both sides) appears once. `BattleState` carries
  derived stats only, never genes. The anchor holds both rosters from the PvP start
  (`tactics::start_pvp_tactical`), because the settlement writes HP back from those teams,
  matched to the monster-id lists by position (`battle::write_back_party_hp`,
  `pvp::write_back_party_hp_pvp_side_b`). While a PvP battle between two players is
  Deploying, `my_battle` returns each participant the anchor with the other side's team
  empty and its active index 0; the monster-id list stays. From the reveal on, for a wild or
  Practice battle, and for a PvP battle closed while still Deploying, the anchor is returned
  as stored.
- **Tactical tables.** The participant views join through `battle`'s identity
  indexes, so a stranger gets nothing; the queue and deploy staging are owner-only,
  and `battle_unit` carries no queue or ready field (`docs/DECISIONS.md`, "Tactical
  battle privacy is structural"). `battle_secret`, `battle_wild_unit` and
  `battle_summary` have no client read path. Deploy is reveal-by-copy: each side's picks
  go to its own owner-only `battle_deploy` row (`locked`, written in `tactics::stage_pvp`).
  The second lock, or the auto-fill when the 45 s window closes (`tactics::expire_pvp_deploy`,
  `pvp_deploy_ms` in `game-core/src/tactics/tuning.rs`), calls `tactics::materialize`, which
  copies both stagings into `battle_unit` rows and flips the phase in one transaction, so no
  unit row exists before both lock and the only participant-visible deploy fact is the phase
  flip. `battle_clock` holds one row per side (a Practice
  battle's two name one player), and both participants read both. `tactics::store` writes a
  row only when it moved, so a pre-queue or a cancel leaves nothing participant-visible.
  Forfeit is its own client-confirmed reducer (`tactics::forfeit`), not a queue entry, and
  costs 0 AP. Game-core's non-wire enums (`Side`, `MoveClass`, `Stance`, `Entry`) are stored
  through schema-local `SpacetimeType` twins (`SideRow`, `MoveClassRow`, `StanceRow`,
  `BudgetLastEntry`), never as integer codes.
- **Leaderboard.** `ranking.rs` is the only writer of `profile`, and its three writers
  (`apply_pvp_rating`, `rekey_profile`, `anonymize_display_names`) end their profile writes
  with `refresh_leaderboard_top`, which `init` and `sync_content` also call. The rescan
  deletes only the members that left and inserts only those that entered, so an unchanged
  membership writes nothing. A publish over existing data runs no `init`, so the table fills
  at the deploy's owner `sync_content` call or the first rated settle, and until then a client
  sees only its own row. The client subscribes
  `SELECT profile.* FROM profile JOIN leaderboard_top ON profile.identity = leaderboard_top.identity`
  and its own row by identity. A member that leaves the top 100 arrives as a profile delete;
  the SDK counts a row once per query that holds it, so the own row survives leaving the top
  100. `ui/leaderboardModel.ts` ranks the rows held and marks the caller's own row `100+`
  when it is not a member.
- **Accepted exposures.** `trade_offer` is public, so the amounts in a row still
  draining from it reveal a lower bound on the offering player's balance; no reducer
  adds rows. The display cards in an offer carry public-projection fields only.
- **Data lifecycle.** `schema::DATA_LIFECYCLE_MANIFEST` gives every table a deletion
  policy (Erase, Anonymize, ViaJoin, NotOwned), a written basis, and an `exportable`
  flag. A test in `accounts_tests.rs` compares it with the generated module
  definition's table set, so a table missing from it or listed but gone fails. The tactical tables are swept by `schema::erase_tactical_rows` (by
  `battle_id`, before the `battle` anchor is tombstoned — the three tactical schedule
  tables included). Of them only `battle_summary` and `player_formation` are exportable: the
  export carries the caller's formation and every summary naming them on either side,
  `Ongoing` rows included, with the other side's identity, idle time and damage as null, as
  for `battle`; a practice row names the player on both sides and is exported whole, and the
  whole-battle columns are exported as they stand. `erase_tactical_rows` collects the battle
  ids from every row that still names the identity (the `battle` anchor chain, the clock,
  queue, deploy and summary identity columns, and a scan of `battle_unit`), sweeps each
  battle's per-battle rows before `battle::anonymize_battles` tombstones the anchor, and
  leaves `battle_summary` with the deleting side swapped to the tombstone identity. The
  other participant's rows of a shared battle go with it: the anchor is forced terminal for
  both sides and the transcript is due for GC. A guest claim runs the same two steps for the
  guest identity it retires; there every anchor is already terminal, because the claim
  refuses while either identity is in an ongoing battle. A finished tactical battle's event, unit,
  queue, clock, secret, wild-unit and staging rows are deleted 24 h later by the
  scheduled `battle_gc`; `battle_tactical`, `battle_summary` and the anchor survive. A
  player's PRIOR terminal anchors are swept at every tactical battle end with
  their tactical rows; only their `battle_summary` rows survive, finalised. `battle_summary`
  itself keeps its newest 100,000 rows (`BATTLE_SUMMARY_CAP`): `summary_reaper` deletes older
  ones whose battle has no `battle` or `battle_tactical` row left. `tactics_settle`'s one
  summary insert reads the row count and, over the cap with no run armed, arms one run 300 s
  out; at or below the cap it writes nothing. A run deletes the lowest ids down to the cap, at
  most 8,192, skipping held rows (a live battle, a finished battle whose anchor is kept until
  its player's next battle, an erased account's tombstoned last battle), and re-arms 300 s out
  only when it stopped at that limit with the table still over the cap. A run that walked
  every row and is still over the cap left only held rows and arms nothing; the next insert
  over the cap arms the next run.

**Tactical battles (`tactics.rs` + `tactics_settle.rs`, M-battle-tactics bt-8/bt-9).** The server is a shell over
`game_core::tactics::queue::TacticalBattle`: a reducer hydrates the bt-7 rows into the
engine, hands it one input (`start`, `advance`, `submit_queue`, `cancel_queue`, `expire`
or `conclude`), writes every row back and arms or disarms the schedule rows the step asks
for. A clock window arms one `tactical_deadline_sched` row pinned by `(battle_id, unit_id,
window_seq)` at the clock's own deadline (a stale or premature fire changes nothing; a
premature one re-arms); a round that completes without player input leaves the battle
`Advancing` with one zero-delay `tactical_advance_sched` row pinned by `(battle_id, round)`;
the Deploying window rides the deadline table with `unit_id 0`, `window_seq 0` and closes
the battle as `Fled` with no HP write. Every step mirrors the deployed units' HP into the
anchor's legacy side-A team, so the one write-back primitive (`battle::write_back_party_hp`)
persists damaged HP at every tactical terminal; a battle whose rows can no longer be loaded
(content drift) is closed by a fallback that writes each unit's HP to its monster row only
while that monster still belongs to the unit's owner, and a tactical row whose anchor is
already terminal closes with no HP write at all — the scheduled reducers never leave a
tactical battle `Ongoing`. Every close goes
through one `finish`, idempotent against the stored row, which hands `tactics_settle::settle`
the close kind. Forfeit, disconnect, the fourth auto-pass, Surge and adjudication all reach
`finish` as `Close::Settled`; a PvP battle settles through `pvp::settle_pvp_battle` in
`SideAWriteBack::HpOnly` mode, the one caller of `ranking::apply_pvp_rating`, and for a PvP
battle the settlement pays essence to both sides, with no XP and no currency. A Practice battle
is neither rated nor paid. Settlement (design §7): the reward ledger is a fold of the persisted
transcript — each `Ko` is credited through `game_core::tactics::rewards::on_unit_defeated` to
the attacker of the last opposite-side hit on the victim, against the board as it stood at
that moment (the final board with the units not yet fallen restored: consciousness is
monotone, nothing heals mid-battle); `rewards::pay` pays only the units conscious at the end,
on every terminal path alike, through the carried per-monster credit
(`battle::credit_monster`) over the whole conscious party, so the win-only trust-favorable
credit, Quality Time and the evolution check keep their carried scope; the currency goes to
the wallet; one `Awards` line per paid monster (ascending unit) plus one `unit 0` line for
the currency is appended after `BattleEnd`. The faint penalty
(`battle::apply_faint_penalties`) and the
prior-terminal sweep run from the same place, so a recruit success penalises and sweeps like
every other end. `battle_summary` is one row per battle: inserted at the Active start (an insert
that takes the table over its cap arms `summary_reaper`),
accumulated every step (windows per unit-turn, pre-queued vs live turns, halted pre-queued
plans, hits/misses, recruit attempts, items, autopasses, single-hit super-effective KOs after
round 1) and finalised at the end (`outcome == Ongoing` marks an unfinished battle). The
recruit glue is the `Hooks` impl: the bait's content row, the wild's seed row, species and
level are resolved before the executor debits the bait, the roll is game-core's
(`recruit::resolve_recruit`, the private stream), the H1/H2 `playtest_event` row is written
with the pre-roll HP, and a success rebuilds the wild through `taming::insert_recruited`;
`Item` entries stay refused (no game-core rule home yet). One anchor, one payout path: no
client-callable 1v1 reducer exists, and no scheduled one.
The module declares none of the 1v1 tables `battle_action`, `battle_wild` and
`pvp_deadline_schedule`, the scheduled `pvp_deadline_reaper` or the `PvpAction` type, and tests
over the generated module definition hold that none is declared.

The `battle-schema-snapshot` and `spacetime-type-snapshot` evals record every table's
columns and every nested `SpacetimeType` in `evals/baselines/`, so an unplanned
migration-breaking change fails `just eval`. `client-surface-privacy` checks the
generated bindings against the allowed client-visible tables and client-callable
reducers (`evals/baselines/client-visible-tables.json`,
`client-callable-reducers.json`). Generated bindings are never edited by hand;
`just gen` regenerates them, and `bindings-drift` fails when they are stale.

Between consolidations a schema change only adds (`docs/DECISIONS.md`, "Schema changes are
additive"). An illegal combination of states that a column-type change would rule out is held by
a checked predicate instead (`accounts::account_state_is_legal` is one). A new table needs an
entry in `schema::DATA_LIFECYCLE_MANIFEST`, and a new column on an exportable table breaks the
compile of the exhaustive export fixtures in `server-module/src/privacy_tests.rs`, which forces
an export-or-omit decision in that table's serializer in `privacy.rs`. A consolidation ships
with a wipe of every database (`docs/runbooks/playtest-ops.md`, "A schema consolidation") and
raises `MIN_CLIENT_PROTOCOL` to the new `PROTOCOL_VERSION`. The two schema evals compare each
baseline with its copy at the merge base and refuse a removal, a reorder or a type change; they
skip that comparison only when the working baseline carries a top-level `consolidation` key
whose value is in the evals' own `DECLARED_CONSOLIDATIONS` list and which the merge-base copy
lacks. `--write` never writes the key, so the next schema change drops it, and a key kept past
that change fails the eval.

## Client

`client/src/main.ts` wires everything; the logic lives in small modules, mostly pure
with thin shells. Code leaves it into owner modules under `client/src/shell/`: the module map and
the owner of each binding are in `docs/refactors/client-shell.md`, and the extractions still to
make are listed in order in `docs/refactors/client-platform.md`. That plan also covers what the
client takes from its host, so that one bundle runs in a browser tab and in a desktop shell: each
such capability has one owner, listed there by call site. Most are web APIs every host provides,
reached through a narrow type the real global satisfies (the storage hosts, the pad read, the key
event, the media query, the window size) or a DOM listener `main.ts` or `connect` registers; a
capability a second host must provide differently gets a port under `client/src/platform/`, whose
default is the browser's code; the plan's first extraction creates the first of them.
`shell/config.ts` holds the values fixed for the session,
set at import: the connection target (`URI`, `DB`, `TARGET_KIND`, resolved from the shell
document on the page global; a production build throws at import when the document is missing
or refused), the dev-log level and its send and fate
loggers, the zone id, the game-core constants read from the wasm exports, and the wasm-ready
mark. It writes nothing to the document and registers nothing. `shell/views.ts` owns the handles
of the views built at boot (the screens, the Profile sections, the session overlay, the

the view is mounted. The module imports types only. `shell/inputState.ts` owns the live input
devices: the keyboard and pad binding tables (read from storage at import), the source built over
each, the router, the held directions, and the key codes of consumed presses, whose OS repeats are
cancelled. Only it replaces the tables and the keyboard source (`applyTables`, which saves both
tables in one record and releases everything held first), and the set of codes is read-only to every
other module: a consumed press is recorded with `noteNavHeld` and its keyup with `releaseNavHeld`.

`main()` builds, `pumpAnnouncements` is the frame loop's announcement edge and notice step, and

### Connection and store

`net/connection.ts` builds the SpacetimeDB connection from the target in `shell/config.ts`
(`URI`, `DB`). The host sets that target in a page global: `index.html` loads a classic script,
`/shell-config.js`, as a `<body>` child before the module script, and it assigns
`globalThis.__MR_SHELL_CONFIG__` to the shell document `{ connection: { uri, db, kind, fingerprint }, host }`.
`net/shellDocument.ts` owns the global's and the script's names, the four kinds (`official`,
`test`, `local`, `private`), `readShellDocument` (the global's own value only) and
`renderShellConfigScript`. `net/connectionConfig.ts` holds the one resolver, which rejects and
never clamps. With no document a development build joins `ws://127.0.0.1:3000`, database
`monster-realm`, kind `test`, and a production build throws. A present document must hold only
`connection` and optionally `host`; `connection` holds `uri`, `db` and optionally `kind` and
`fingerprint`; anything else throws in every build. `fingerprint` (the world's certificate
key's fingerprint, 1 to 128 characters of `A-Z a-z 0-9 - _`) and a top-level `host`, whose
only value is `'desktop'`, are accepted with every kind and exported by `shell/config.ts` as
`WORLD_FINGERPRINT` and `DESKTOP_SHELL`. `uri` is an absolute `ws:`/`wss:` URL with no
userinfo, query, fragment or
whitespace, and a path ends in `/` and holds no `.` or `..` segment (the SDK resolves its
endpoints relative to it, so any other path would dial a prefix the string does not name). `db`
matches `[A-Za-z0-9_-]+`, and a production build also refuses `monster-realm` in any letter
case. An omitted `kind` is `test` in development and `private` in production. `uri` and `db`
are the document's strings trimmed and otherwise unchanged, because `net/authToken.ts` and
`net/claimCode.ts` key the reconnect token and the claim code on them. Errors name the field
and never echo a value. The Vite plugin `mr-shell-config` (`client/vite.config.ts`) takes
`VITE_STDB_URI`/`VITE_STDB_DB` as its inputs: `vite dev` serves `/shell-config.js` with kind
`test`; `vite build` writes `dist/shell-config.js` only when `VITE_STDB_DB` is set, after
resolving it as a production client would; `vite preview` has no hook and serves the built
file. Each connection first subscribes `module_info` alone and judges its row 0 against the
client's own `protocol_version()` (`net/protocolCheck.ts`, pure). A server whose protocol is
below the client's, that holds no row or that refuses the query is its host's to update; one
whose `min_client_protocol` is above the client needs a newer game. Either refusal ends the
connection for the life of the page: nothing further is subscribed or sent, no reconnect
follows, and `main.ts` names the side to update on the world hint line until reload. An admitted connection is judged again whenever that row changes, and only toward
refusal. Once admitted, the connection subscribes to the public tables it renders (never the
drain-only `trade_offer`) and the owner-scoped views in one batch, the base set of 30
queries. `player` is in it, world-wide. `character` is not: it is the one public table
written on every step, so the connection holds it as query sets of their own, one for
the own row (`WHERE entity_id = …`) and one per wanted zone (`WHERE zone_id = …`).
`net/worldScope.ts` owns those two query strings and the state of the sets, as pure
functions: which sets are wanted, pending or applied, when an unwanted one is released
(after `LINGER_MS`, and never before the own zone's set is applied), and when a
rejected or never-applied set ends the connection. `connection.ts` executes its
effects: it re-evaluates the scope after every change to the own `player` or
`character` row, after each set's applied or error callback and on a 500 ms timer, and
discards the scope with the connection. The wanted zones are the one the own row is in
and the destination of each warp within `PREFETCH_TILES` (4) of that row's tile;
`main.ts` gives the connection each zone's warps (`zoneWarps`, from the content's zone
map). A destination is thus held before the warp and drawn on the arrival's first
frame. On a warp the own row's update callback calls `onOwnWarp`, stores the row and
subscribes the new zone if it is not held yet, in that order. The scope is settled when the own-row set and
the own zone's set are both applied; `main.ts` draws no character on a new connection
until then, so a login or reconnect never shows the player alone in an empty zone. The
store therefore holds the own character, the characters of the own zone, and those of
a zone behind a nearby warp or still lingering, which the render filter leaves out. The SDK fires per-row
callbacks.
`net/batch.ts` coalesces a transaction's callbacks within one microtask so the store
flushes once per burst, and the predictor reconciles against a consistent snapshot.
`net/rowConvert.ts` and `convert/convert.ts` convert SDK rows (tagged unions,
`bigint` ids) into store and wasm shapes, explicitly and without abstraction.

Views behave differently from tables on the client. None of the module's views
declares a primary key, so the SDK never fires `onUpdate` for a view row: a change
arrives as an unordered delete and insert. The owner views (`my_monster_pub`, `my_battle`,
`my_inventory`, the tactical views and the others in `net/viewReconcile.ts`'s
`OWNER_VIEWS`) are therefore rebuilt whole from the SDK's cache rather than applied row by
row. A view's row events only mark it dirty, and before each flush `viewReconcile.ts`
rebuilds the dirty views and no others, so a batch of `character` or `player` rows rebuilds
none. Every owner view is marked when the base subscription's snapshot applies, when a
connection is built, when the store is reset, and when another table's row handler throws
(the SDK then skips the rest of that message, whose rows are already in its cache).
`createOwnerViewReconciler` (`markDirty`, `markAllDirty`, `reconcileOwnerViews`) holds the dirty
set. `connection.ts` loops over `OWNER_VIEWS` to give each view's `onInsert` and `onDelete` handlers
their mark; `markAllDirty` runs beside `store.reset()` on a drop, after every build's `wireTables`,
and first in the base subscription's `onApplied`. A view is cleared once its reconcile returns, and
a throw leaves it and the later dirty views of its try group dirty for the next batch. Every
non-view row handler is wrapped in `recoverViewsOnThrow`, which marks every view, schedules the
flush and rethrows. A new owner view gets a `RECONCILE` entry and a `TRY_GROUPS` slot.
`my_conversation`, `my_wallet` and `my_account` are views too, but are ingested row by row.

`net/store.ts` is a read-only mirror of the subscription. Only the connection adapter
writes to it; the predictor and renderer only read (`server → store → render`). It
keeps up to four timestamped snapshots per character for interpolation, one per
position (a row update on the same tile replaces the row and adds no snapshot), the
character's last two position changes and whether it has turned in place since, and a
per-character jitter estimate taken from the intervals between position changes.

Reconnect uses exponential backoff from 1 s to 30 s (`prediction/reconnectPolicy.ts`, a pure
state machine `net/connection.ts` drives). `attemptBuild` is the one caller of the build, so every
build path starts an attempt there: the reconnect timer, the first boot, `reconnectNow` and
`continueAnonymously`. The shared drop path (`handleDrop`) counts the drop of an attempt that never
applied as that attempt's failure, and shows "connection lost" only on the connected-to-disconnected
edge and never on a page the protocol check refused.
The SpacetimeDB token for an anonymous identity is kept where the host and the target's kind
say (`tokenPersistenceFor(kind, desktop)` in `net/authToken.ts`). The origin's `localStorage`
holds it only when the shell document carries `host: 'desktop'` and the kind is `local` or
`private`, so a relaunch of the desktop shell resumes the same player. Every other case, a
page in a browser for every kind included, keeps it in per-tab `sessionStorage`, so an
identity survives a reload but not closing the tab, and a second tab is a separate
identity; for a `local` or `private` target kept per tab, `connect()` first removes that
one target's token key from `localStorage` (`forgetDeviceToken(globalThis, uri, db)`, once
before its first build). `createAuthTokenGate` takes the choice and uses exactly one area, never
the other. `ConnectionOptions.targetKind` is required and `desktop` defaults to a browser;
`connect()` builds its one gate from the two, and `main.ts` passes `TARGET_KIND` and
`DESKTOP_SHELL`. `net/authToken.test.ts`, `net/connection.runtime.test.ts`,
`main.targetKindGate.test.ts` and the browser spec `client/e2e/local-identity.spec.ts` hold the
rule. After two token
rejections since the last
successful connect, the client stops sending the stored token (it never deletes it) and
connects anonymously. If that connect succeeds, `onConnected` stores the new token over
the old one; a network failure never counts as a rejection, so an outage cannot cost
the player their identity. Sign-in is OIDC (authorization code with
PKCE, `net/oidc.ts`) against the issuer in `VITE_MR_OIDC_ISSUER`. `main.ts` hands
`connect` the issuer and client id only for a target of kind `official` or `test`; a
`local` or `private` target gets both empty and connects under the anonymous token.
The Profile screen's Account section offers Sign In only when `connect` received an
issuer, labelled with the build's `VITE_MR_OIDC_PROVIDER_NAME` (the issuer when the
build names none); `signInOffer` in `ui/claimModel.ts` decides it from that one value.
`main.ts` reads `VITE_MR_OIDC_ISSUER` in one module-scope assignment that keeps it only for
`official` or `test`; any other kind holds the empty string. `VITE_MR_OIDC_CLIENT_ID` reaches
`connect` under the same kind test. `connect` gets `signIn: 'oidc'` only when that issuer is

### Prediction and reconciliation

`prediction/predictor.ts` runs the wasm `apply_move` locally so a keypress moves the
player immediately:

1. **Intent.** `enqueue`, `setMove` and `clearQueue` record a queue operation with the
   next `seq` and return it for sending. `enqueue` refuses past `MOVE_QUEUE_CAP` and
   at 16 unacknowledged operations.
2. **Drain.** Each frame, `drain(now)` applies due moves at `STEP_MS` cadence, at most
   the queue cap per drain. After a long gap (a backgrounded tab) it reports `snapped`
   so the renderer jumps instead of replaying.
3. **Reconcile.** On each flushed batch, `reconcile` drops acknowledged operations
   (`seq <=` the own character row's `acked_seq`), rebuilds the queue from the server's
   `move_queue`, replays the pending operations, resets to the authoritative position,
   and drains. It reports whether the corrected tile differs from the prediction. The
   server publishes the ack and the queue only with `movement_tick`, so an accepted
   input stays a pending operation until the tick that drains or publishes it; a page
   that loads while its rows survive can seed from an ack one tick old, and its first
   send is then rejected as stale and re-issued.
4. **Rejections.** A rejected intent is removed with `dropRejected(seq, epoch)`,
   followed by a forced reconcile. The epoch makes a rejection addressed to a
   discarded predictor (after a warp or reconnect) a no-op, and rebuilt predictors
   start above the highest seq already sent.

Held keys (`prediction/heldKeys.ts`) keep a most-recent-first stack of held
directions. A press sends `Face` at once: a turn in place for a character that faces
another way, a step for one that already faces the direction. The frame loop continues
a hold with `Step` in the active direction only after it has been held 150 ms
(`HOLD_COMMIT_MS`), only when the predictor has no outstanding steps and no sent input is still
owed, and only while `movementGate()` in `main.ts` passes: `movementEnabled` (`ui/contextStack.ts`:
the world base with no frame above it and the session gate open) and no world sheet open. A hold
from another facing therefore turns, waits for the row that drains the `Face`, then walks. The
reconcile listener re-sends the held direction behind the same checks after a server correction.
Every push of a frame, and every change of base kind, clears the held set. The keyboard source
drops OS key-repeat (`e.repeat`), and the router (`input/router.ts`) counts each D-pad button's
holders across physical keys and synthesizes menu auto-repeat on an injected clock
(`REPEAT_DELAY_MS` 350, then every `REPEAT_PERIOD_MS` 100); a repeated step clamps at an end
where a fresh one wraps (`stepAxis` in `ui/nav.ts`). A zone
warp (`switchZone` in `main.ts`) rebuilds prediction state but keeps the held stack; a reconnect
(`resetPredictionState`) clears it. The rebuilt predictor has forgotten an
input that was on the wire at the warp, so `prediction/owedInputs.ts` counts sent
inputs outside the predictor: each stays owed until the own row's `acked_seq` covers
it or its reducer call rejects, and a reconnect clears the set.

### Rendering

`render/` splits into pure cores and a Pixi shell:

- `slideClock.ts` animates the own character on a local clock keyed to target-tile
  changes. It ignores the server's `move_started_at`, which is re-stamped every tick
  and would restart the slide.
- `interpolation.ts` renders remote characters in the past between buffered
  snapshots, with an adaptive delay, holding at the newest snapshot. The delay is per character,
  from the store's jitter estimate, which ignores intervals longer than `JITTER_IDLE_GAP_STEPS`
  (3, `shared/interpConfig.ts`) steps, and is clamped between `INTERP_MIN_DELAY_STEPS` (0.5) and
  `INTERP_MAX_DELAY_STEPS` (2.5) steps (`render/config.ts`). A remote on a
  straight walk is the exception: it is continued at most half a tile past its newest
  tile, at the walk's own cadence. A gap of up to three steps between two steps of a walking
  remote is crossed at the walk's pace, not held and then slid. The file also has the slew that
  walks a drawn position to its target one axis at a time, and a reduced-motion path.
- `renderResolver.ts` sends each character to the right one of those two and snaps
  the own character when the authoritative target is more than one tile away. For
  remotes it keeps each one's last drawn position and moves it toward the frame's
  target at no more than one tile per step, or draws it at the target once that is two
  tiles or more away. It continues a walk only for three steps after the remote's
  newest step and only toward a tile the zone map allows; `main.ts` passes that map's
  walkability in every frame.
- `map.ts` parses the tile map once from the wasm `zone_map()` value; `camera.ts`
  follows the player and centres maps smaller than the viewport; `viewport.ts` picks
  an integer device scale aimed at `TARGET_VISIBLE_TILES` (11) on the shorter axis, never more
  than `MAX_VISIBLE_TILES` (16) and at least `MIN_VISIBLE_TILES` (7) where the viewport allows
  (`render/config.ts`), and its `appInitOptions` runs Pixi at
  `resolution` = `devicePixelRatio` with `autoDensity`; `viewRegistry.ts` pools one sprite per
  entity and tears it down on despawn.
- `world.ts`, `characterView.ts`, `atlasAssets.ts` and `placeholderAssets.ts` are the
  Pixi shell. Tiles are drawn at `TILE_PX` (32). Characters draw from the hero atlas
  (`atlasAssets.ts`), and from `placeholderAssets.ts`'s monochrome shapes when the atlas
  fails to load; both show facing and action without depending on colour.

**Scale.** `viewportScale` (`render/viewport.ts`) is the one scale function. It returns the
integer `deviceScale` the world renders at and the continuous `uiScale`, the shorter CSS axis over
720 clamped to [0.875, 3]. `installResizeHandler` writes `uiScale` to `--mr-ui-scale` on
`documentElement` at the same event that resizes the renderer, and `world.ts` reads the same
function at that event. The one root rule,
`:root[style*="--mr-ui-scale"] { font-size: calc(100% * var(--mr-ui-scale) * var(--mr-text-step, 1)); }`,
carries it to every rem token; until the first write it does not match and the root stays at
100%. The player's text size (×1, ×1.5 or ×2, from Controls › Display, `ui/displayPrefs.ts`) is
`--mr-text-step`, written at import, before the first scale write. The selector is keyed on the
write because happy-dom cannot compute rem through a `calc()` root font-size (it reads `NaNpx`),
and suites such as `frame.test.ts` load the real sheet without the resize seam.

**One frame owner.** `appInitOptions` sets `autoStart: false`, so Pixi's own render ticker stays
stopped; `WorldRenderer.render` draws once at the end of each frame-loop frame, and
`WorldRenderer.resize` draws because a resize clears the canvas. The renderer caps
`renderer.limits.maxBatchableTextures` at `MAX_BATCH_TEXTURES` (4, `render/config.ts`) after init
and after every WebGL context restore. On a restore it also re-bakes the terrain chunk textures and
drops the generated placeholder character textures (`AssetProvider.contextRestored`). The
flat-terrain fallback's large `Graphics` uses a separate Pixi shader built at the device limit,
which the cap does not reach. `client/e2e/render-context.spec.ts` loses and restores the context in
a real browser, compares the canvas before and after, and counts one canvas clear per animation
frame.

**Terrain grammar.** Each zone-map glyph is a terrain class. The class table is
`TileKind` (`game-core/src/types.rs:96`), and it is the one source of glyph,
walkability and encounter flag (`TileKind::from_char`, `types.rs:141`;
`is_walkable`, `types.rs:194`). The wasm `zone_map()` payload carries a row-major
`terrain` layer of wire names. `map.ts` parses it against `TERRAIN_KINDS`
(`client/src/render/map.ts:28`), whose list a test pins to the wasm export, and serves
it through `TileMap.terrainAt` (`map.ts:214`). The client never derives terrain from
`walkable`/`grass`. `terrainLayout.ts` turns each tile's class into one kit frame key
(`layoutTerrain`, `client/src/render/terrainLayout.ts:186`). It picks a per-tile
variant, uses a shore frame where shallow water meets land (`shoreMask`,
`terrainLayout.ts:128`), and gives water its animation frames. A missing kit, missing
terrain layer or missing frame gives the flat-rect fallback with one warning.

**Art registry.** `client/src/render/art/registry.ts` holds one provenance row for every
PNG served from `client/public/assets/` (`ART_REGISTRY`, `registry.ts:126`), aggregated
from one pack file per asset family under `render/art/packs/`. The packs are terrain,
characters, landmarks, monsters, battle and grade. `validateArtRegistry`
(`registry.ts:91`) and the row types reject image-model output and unaccepted licences. A row
records the stable atlas key, file, kind, sheet and frame size, scale, source (the generator path,
or the pack's URL), license and provenance tag; a row for a file from a generator since deleted
cites it as `<path>@<commit>`. The validator rejects a duplicate key or file, a sprite, tile or
normal frame off the 16 px grid, a scale other than 1, a malformed key and an empty attribution.
Its colocated test runs it over the real rows and checks each row against the served directory and
the PNG headers.
Each row's atlas key is stable, so final art is a file swap. The packs also export what
the renderer loads. `TERRAIN_KIT_CLASSES` (`render/art/packs/terrain.ts:60`) maps each
class to its frame keys, and `LIVE_KEYFRAME` (`render/art/packs/grade.ts:13`) is the
grade the game uses, `day`.

**Render layers.** `WorldRenderer.init` builds one world container holding three layers in
draw order (`client/src/render/world.ts:296-299`): terrain (`#bg`), ground decor
(`#decor`, the warp markers) and actors (`#actors`, z-sorted by row,
`world.ts:302`). The world container is the stage's only child; the UI is DOM, outside
the canvas.
- Terrain (`#drawMap`, `world.ts:461`): `planChunks` bakes static tiles into
  nearest-sampled chunk textures at resolution 1 (`world.ts:489`; the chunk cache in
  `render/terrainLayout.ts` bakes with its `CHUNK_TEXTURE_OPTIONS`), which the integer device scale
  upsamples, so a device-scale change re-bakes nothing; a WebGL context restore re-bakes them.
  Animated water stays as per-tile sprites whose texture changes only when the frame index
  changes. The bake runs before the drawn terrain is torn down, so a failed bake leaves the previous
  terrain on screen.
- Decor (`#drawDecor`, `world.ts:521`): `layoutDecor` (`render/decorLayout.ts:56`)
  places a landmark per heal-location row and a warp marker per warp source tile, from the
  map's content rows. Landmarks are two tiles tall and join the actors' row z-order. Warp
  markers are ground decals under every actor.

**Post stack.** `planPostStack` (`client/src/render/postStack.ts:151`) is a pure plan.
From the toggles, an injected `nowMs`, the reduced-motion bit, the keyframe and the
renderer's resolution, it returns the enabled passes in `POST_PASS_ORDER`
(`postStack.ts:21`): ambient lightmap with a vignette, AdvancedBloom, Godray and a
ColorMap LUT. `#applyPostStack` (`world.ts:353`) builds exactly those `pixi-filters`
filters and attaches them to the world container only, so the DOM UI is never filtered.
An unsupported renderer, a pass that throws while it is built, or a throw from the probe
frame drawn after the build disables the whole stack with one warning. The
renderer starts with every pass off (`world.ts:255`), and the live game keeps it off
(DECISIONS.md "The world post stack is `pixi-filters`…"). The filters are `pixi-filters` `6.1.5`,
pinned exactly in `client/package.json` and imported by subpath (`simple-lightmap`,
`advanced-bloom`, `godray`, `color-map`). The plan also takes what the renderer supports; each
filter runs at the renderer's resolution, and the LUT samples `nearest`. The godray time is
`godrayTime(nowMs, reduceMotion)`. The software-rasteriser check a build that turns the stack on
needs would read `UNMASKED_RENDERER_WEBGL`. `setPostStack`
(`world.ts:343`) turns passes on: the look-dev scene uses it, and the world-art e2e uses
it through the DEV `__game().setPostStack` hook.

`WorldRenderer.describeArt()` (`world.ts:717`) is a read-only account of what was last
drawn. It reports the terrain kind (kit or fallback), the kit frame key per tile, the
per-class tile histogram, the landmark and warp-marker sprites with their screen rects
(via `screenFor`), and the attached passes with their keyframe. The DEV
`window.__game().art` field reads it, and `client/e2e/world-art.spec.ts` asserts the
whole flow through it.

The frame loop in `main.ts` (`requestAnimationFrame`) drains the predictor, resolves
positions, and draws.

### UI

Input is a console-style pipeline of virtual buttons (`input/buttons.ts`: the D-pad, A, B,
X, Y, LB, RB, Start, Select). Three sources feed it: `input/keyboardSource.ts` maps keys through
the remappable binding table (`input/bindings.ts`, saved by `input/bindingStore.ts`, drawn by
`input/glyphs.ts`), `input/gamepadSource.ts` polls every connected pad once per frame through the
remappable pad table (`input/padBindings.ts`), and `input/pointerSource.ts` is ONE dispatcher on
`#game-screen`. A click on the canvas at the world base is A (no coordinates). A click on a row of
the top frame is a seek: the D-pad presses that walk that list's cursor there, then A. The
first press is a probe: if the clicked list's cursor did not move as planned, it is undone and nothing is activated. A click on a tab is LB/RB. A right-click, or a touch long-press
(`input/longPress.ts`, 500 ms within 10 px, with a fill ring), is B, or cancels a remap capture.
The pad leaves a waiting Controls cell with the button a Pad cell shows, else with B.
Under the session terminal (`ui/sessionView.ts`) no pad press reaches the router: the D-pad or the
stick moves over the terminal's buttons, A presses the focused one, and every other button does nothing.
A hint-bar chip presses its button. The mouse hovering a row moves the cursor there. All three
hand button edges to `input/router.ts`, which decides walking, menu navigation or a screen button
from the context on top. Two clicks skip the router: a main-menu row (the menu's own pick) and the
dialogue's choice and shop buttons.

The main menu (`ui/menuModel.ts` `MENU_ENTRIES`, drawn by `ui/menuView.ts`) is one flat list of
eight root rows with no sub-lists: Monsters (`boxView`, Party and Storage tabs), Inventory
(`raisingView`, one tab per pocket), Journal (`questLogView`), Social (the four-tab Social frame:
Players, Trades, Challenges, Rankings), Profile (`profileView`, ONE dialog whose Name, Account and
Privacy sections are one D-pad column), How to Play (`helpView`: Introduction and Encyclopedia
tabs), Controls (`controlsView`: Buttons, Shortcuts and Display tabs, the text-size setting under
Display) and Close. There is no Options group. Each leaf opens above the menu and B returns to the
menu on that row; a menu left on Close reopens on Monsters. Tabs render through the one TabBar
(`ui/tabBar.ts`) and per-item mini-menus through the ContextSheet (`ui/contextSheet.ts`);
`client/e2e/ui-whole.spec.ts` walks the whole set by D-pad as the integrated proof of the kit.

The context stack (`ui/contextStack.ts`) is the base (world or battle) plus the frames above it.
`SCREEN_POLICY` says what a battle or a server conversation closes, and `reconcile` mirrors server
truth into the stack. Each frame's screen adapter (`ui/screens/`, keyed by frame in
`SCREEN_ADAPTERS`) turns a button into a nav step or a command. `main.ts` runs commands through
`dispatch` and applies stack changes through `applyStack`. `ui/overlayRegistry.ts` still decides
which overlay may open over which (`canOpen`), its accessibility metadata (`OVERLAY_A11Y`) and
which are visible. Frames are built from `ui/frame.ts` and `ui/navRender.ts` inside
`#game-screen`'s frame layer. The hint bar (`ui/hintBarModel.ts`, `ui/hintBar.ts`) is generated
from the context table, the live bindings and the catalog. How to Play (`ui/helpModel.ts`,
`ui/screens/helpScreen.ts`, `ui/helpView.ts`) is catalog copy: an Introduction, ending in a Report a
problem row, and an Encyclopedia of the game's terms, whose entries open as the ContextSheet's detail
variant in the same frame. At
the world base, A acts on the target that the wasm `interact_candidates_coded` export picks: the
entity in front, else on the character's own tile ("server-module: the authority", Reach). The
server checks its own, wider range.

Every input resolves through the binding table to the virtual buttons; the tables persist in
`localStorage['mr.controls']` (versioned), and `PROTECTED_BUTTONS` (`input/bindings.ts`) always keep
a key. `SCREEN_POLICY` is a total record per frame: its owner, battle behaviour and battle safety.
The client closes a server-owned frame only by sending its reducer (`dismissDialogue` for the
dialogue). Every frame is a class-styled `.mr-frame` inside `#game-screen`, and menus are D-pad
lists, grids and tabs (`ui/nav.ts`). `main.ts` routes Escape alone in the capture phase, so a view's
`stopPropagation` cannot trap it; every other key keeps the bubble phase, where text-entry views
shield their fields. Each view keeps its state in a pure model (`*Model.ts`) with a thin DOM view.

**Opening a frame.** Every player open goes through `openFrame` in `main.ts`, which pushes the frame
and then shows its view; `contextStep`'s same-id push no-op is the one dedup. The trade, challenge
and leaderboard panels are the one `social` frame. The visibility mirror sees only `MIRRORED_IDS`
(`ui/contextStack.ts`): `battleView`, which presents the battle base and the terminal outcome, and
`dialogueView`. A player view that closes itself has its frame popped at the next sync
(`hiddenPops`). `main.ts`'s three tables (probes, hide handles, lent views: `overlayProbes`,
`overlayHandles`, `screenViews`) keep rows only for the mirrored ids.

**Hold edge.** A frame's `RouteContext.hold` (`input/router.ts`) lists its hold-capable buttons,
and `HOLD_MS` is 500. A hold reaches the adapter as `NavInput.hold` (`ui/nav.ts`); `resetRepeat` and
`releaseAll` drop an armed press. `battleHoldButtons` (`ui/screens/battleScreen.ts`) lists Y on the
bare tactical battle base while `TacticsBattle.clearPlanHoldable` holds. A Y tap writes the
hold-to-clear line ("Hold F to clear the plan" on the default keyboard; "Y" where the last-used
device binds nothing to it), and a Y hold sends `cancel_queue` through the same path as the
confirmed Clear plan row.

**Battle frame.** `refreshBattle` routes by the tactical row's phase through `battleRenderer`
(Deploying → the deploy panel, Active → the tactical shell, Finished → the results panel, no row →
`none`). `renderableBattle` is the one predicate `reconcileStack` and `refreshBattle` share. The
three roots share the `battleView` record in `OVERLAY_A11Y`, the adopted live region and the focus
trap; the e2e suites find the battle by `[data-testid="battle-title"]` and the shown root's
`aria-modal`.
`activeBattleView`, `tacticalOwnsStart` and `battleHint` read the shown view, never the phase.

**Feedback channels.** `ui/feedbackPolicy.ts` assigns each `MessageKind` its channel, in a table
that `satisfies Record<MessageKind, PolicyRow>`. The world line is `#status`; the toast is one
`.mr-toast` region (`ui/toast.ts`), announced once through `#a11y-live` (the notice pump) and hidden
after `TOAST_MS` of the frame clock. `sendGuarded` names a kind per send site (`SEND_REJECT_KIND`);
`main.ts`'s care, shop and rename outcomes name a kind. The menu strip's hint order is the
wireframes' WF1-A9. The policy test pins the list of action-required toast kinds, and each of them
names an on-screen state that also carries it. The strip has zero layout height: its height and
negative bottom margin cancel, it sits in a 2rem bottom reserve on `.mr-frame` and `.mr-shell`, and
it is sticky with `bottom: -2rem`, because Chromium measures sticky offsets inside the scroller's
padding. Only the main menu's strip shows a persistent hint; on any other frame it is on `#status`.

**Menu tokens.** The `--mr-*` tokens live in `client/src/styles.css`, with the frame, chip and
banner border widths as `--mr-border-width` and `--mr-border-thin` and every color's
`prefers-contrast: more` value in the sheet's last block. The focus-ring checks in
`ui/overlayA11yWiring.test.ts` require 3:1, which `--mr-focus` misses across the light active row.

**Sheets.** A Monsters frame's sheet is `createContextSheet` (`ui/contextSheet.ts`, root
`[data-context-sheet]`) mounted in `#monsters-panel` (`position:relative`, `ui/boxView.ts`) and
placed by `anchorSheet`. Its row ids are `monstersSheet-root-<key>`, and the heading keeps
`monsters-sheet-name`. A sub-list ends with Back (key `back`, `BACK_KEY` in `ui/monstersModel.ts`),
painted with `kit.sheet.back`; the Close row is `kit.sheet.close`. The Social row sheet's Back is
appended in `ui/screens/socialScreen.ts` and `ui/tradeView.ts`. The world sheets (the picker and
the Y action sheet of `ui/actionSheetModel.ts`, the request sheet of `ui/noticeModel.ts`, the
Challenge party-size confirm) paint inside `#interact-prompt` and are not placed by
`placeContextSheet`; their Close row is `CLOSE_KEY`, a layout row and not a `SheetEntry`. A fresh
Select over one closes it and falls through to the base (`worldButton` in
`ui/screens/worldScreen.ts`, `baseButton` in `ui/screens/index.ts`), which answers `toggleHelp`.
The chip-only prompt is `pointer-events:none`.

**Profile.** `profileView` (`ui/profileView.ts`) is the one overlay; `renameView.ts`, `claimView.ts`
and `privacyView.ts` are its sections and not `OverlayId`s (the overlay manifest test,
`OR-MANIFEST-COMPLETE` in `overlayRegistry.test.ts`, names the three files as an exclusion). Its
`SCREEN_POLICY` row is player / drop, and `RECONNECT_CLOSES` is true for it; `onReconnect` shows a
claim prompt its own cycle raised again after the sweep. When a render refuses the focused control,
the reseat target is the frame's Close (`fallbackRow`). The body does not take the list scroll cue
`.mr-scroll`, and no section has a reset in `RECONNECT_RESETS`.

Strings come from `ui/i18n/`: a `MessageId` union, total catalogs for `en` and `fr`, a
resolver whose `t()`/`tf()` throw on a missing key, CLDR plural rules, and boot-time
locale negotiation from `navigator.languages` (`locale.ts`). Accessibility is
first-class: status conditions on the tactical board are named by the exhaustive
`tactics.status.*` catalog keys (text, never colour alone), focus
is trapped in modals (`focusTrap.ts`), announcements go through live regions
(`liveRegion.ts`, `announcements.ts`), and `Element.animate` is banned
(`client/lint/no-waapi.grit`, a Biome plugin) because it ignores `prefers-reduced-motion`.
`setLocale` throws on an unregistered locale. One whole-tree scan
(`ui/i18n/hardcodedStrings.test.ts`) asserts that no non-test client file writes a raw string to a
text sink; its sink floor only proves the scan still sees the tree, and each view's «key»-sentinel
runtime tests own its behaviour.

The constructed overlays (the battle frame's three roots under `client/src/tactics`, the box,
raising and evolution views) follow one a11y wiring contract (`ui/overlayA11y.ts`): the root is
created and appended into the shared `#app` mount, so every ARIA attribute comes from
`openOverlayA11y`, never from a literal in the view; `show()` reads "was visible" as its FIRST
statement, because a re-open tears down and re-schedules the deferred focus and drags focus off the
control the player had reached; `hide()` calls `closeOverlayA11y` UNGUARDED (a no-record close is a
pure no-op, a guarded close leaks a capture listener, a timer and a return target whenever a record
desynchronises from the DOM); and the open is the LAST statement of the open path, after the display
write, since `.focus()` on a `display:none` node is a silent no-op. Each `#app`-mounted view owns its
root, so opening one never closes a sibling.

### Diagnostics

- `F9`, or How to Play's Report a problem row (the battle-safe `reportProblem` command, which
  calls the same `downloadBugBundle` in `main.ts`), downloads a bug bundle (`ui/bugBundle.ts`)
  assembled locally from the recent event ring (`eventRing.ts`), captured errors
  (`errorRing.ts`), a projected store snapshot without names, and the build stamp (git
  short SHA and build time injected by `vite.config.ts`, `net/buildInfo.ts`). Nothing is
  sent over the network.
- Uncaught errors show a non-blocking toast that `B` at the world base or `F8` dismisses.
- DEV builds expose debug hooks (`__game`, `__mrTrade`, `__mrPvp`) inside an
  `import.meta.env.DEV` branch; `scripts/verify-build-hooks.mjs` checks that a
  production bundle contains none, that the build's `shell-config.js` names the playtest
  database, and that no other file in the build contains that name.
- `VITE_MR_DEVLOG` enables a DEV console log of outbound reducer calls
  (`net/devLog.ts`).
- Client telemetry (`observability/`) exports OpenTelemetry metrics over OTLP/HTTP to
  `VITE_MR_OTLP_ENDPOINT` when set and the target kind is `official` or `test`
  (`resolveTelemetryConfig` takes `TARGET_KIND` from `shell/config.ts` as a required parameter
  and runs an exhaustive `switch` on it before it reads any env value: only `official` and `test`
  reach the endpoint and interval rules, and a `local` or `private` target never loads the SDK).
  It fails silently, loads the SDK only when
  enabled, and labels metrics with a small allowlist of attributes.

## Accounts lifecycle

- **Anonymous by default.** Every connection has a SpacetimeDB identity. Game data is
  keyed by that identity; there is no account row and no PII.
- **Signing in.** With OIDC configured on the client and a target of kind `official` or
  `test`, sign-in redirects to the issuer and reconnects with the resulting JWT. Toward a
  `local` or `private` world `connect` is given no issuer or client id and runs with
  sign-in off: it builds no OIDC client, every connection is anonymous, no OIDC request
  leaves the page and the Account section offers no Sign In. `on_connect` creates an
  `account` row only when the token's issuer and audience match
  `ALLOWED_ISSUERS`/`ALLOWED_AUDIENCE` (`server-module/src/accounts.rs`). A token from an
  issuer not on the list falls back to anonymous play; one from an allowed issuer with another
  audience is disconnected. The build's
  login-issuer list comes from `BUILD_PROFILE`, computed from the cargo features;
  `PRODUCTION_LOGIN_ISSUERS` and `DEV_LOGIN_ISSUERS` hold the values. The production list is
  still the fail-closed `.invalid` placeholder, so no account can be created until a
  real issuer is deployed and the constants are changed. `ops/auth/README.md` has the deployment
  steps and the client build variables (`VITE_MR_OIDC_ISSUER`,
  `VITE_MR_OIDC_CLIENT_ID`, `VITE_MR_OIDC_REDIRECT_URI`,
  `VITE_MR_OIDC_PROVIDER_NAME`).
- **Claiming guest progress.** The client mints a 64-hex-character claim code
  (`crypto.getRandomValues`, `net/claimCode.ts`), stores it per tab, and calls
  `start_guest_claim(code)` as the guest before redirecting to sign-in. The server stores it
  in the private `guest_claim` table with a 15-minute TTL (`CLAIM_TTL_MS`) and a one-shot
  reaper. After sign-in, the account calls `complete_guest_claim(code)`. Guards run in
  order: signed in, holds an account, not deleting, not already claimed, well-formed code,
  live claim, not expired, not its own session, guest no longer connected, neither side in a
  battle, and the account owns no game data yet. Then `rekey_all` moves the guest's
  persistent game data (monsters and their public projection, evolution notices, inventory,
  quests and dialogue state, heal cooldown, saved position, wallet, profile, formation and
  handle) onto the account; the retired guest keeps a tombstone dialogue row (see The
  starter). Then the guest's export bundles are purged; its world rows (admission and
  wrong-password record, binding and bind nonce, `world_account` row with its armed
  re-check, move record) are erased, not moved, so a retired guest identity that reconnects
  holds no world row; its finished battles are erased as the deletion cascade erases its
  subject's (`schema::erase_tactical_rows`, then `battle::anonymize_battles`: the per-battle
  tactical rows go, and the guest's side of each `battle` and `battle_summary` row becomes
  the tombstone identity); the code is consumed, and `claimed_from`/`claimed_at_ms` are
  stamped. Session and in-flight rows (player, conversation, sessions, battles, trades,
  challenges) are not moved. "Owns no game data" works because `join_game` is a reducer the
  client calls, not part of `on_connect`: on a signed-in connection with an unconsumed claim
  code stored, `net/connection.ts` skips `join_game` and calls `complete_guest_claim` first.
  It joins only once no unconsumed code remains, or the player declines the claim. An
  account that already played before claiming fails the claim with "already has game data".
- **Deletion.** `delete_account` sets `PendingDeletion` and arms a one-shot reaper
  `DELETION_GRACE_MS_DEFAULT` (7 days, `game-core/src/accounts/deletion.rs`) out;
  `cancel_account_deletion` reverses it and declines trade offers made to the account,
  and trade sessions opened with it, after it asked to be deleted. While deletion is pending, the account cannot start
  new battles, trades, challenges or other writes (`guards::require_not_deleting`),
  but commitments made before the request can still finish. The reaper resolves live
  interactions, forces ongoing battles to a terminal result, erases or anonymises
  every table per the manifest, and stamps `terminal_at_ms`. `Anonymize` also covers
  `leaderboard_top`, which holds only an identity its anonymized `profile` row keeps: the
  cascade re-derives it after tombstoning the name instead of overwriting it. A later sign-in
  with the same identity starts a fresh account.
- **Export.** `request_data_export` (`server-module/src/privacy.rs`) writes the caller's
  exportable tables as JSON chunks of `EXPORT_CHUNK_ROWS` (500) rows into the private
  `export_bundle` table, read back through `my_export_bundle`. It enforces a per-caller
  cooldown, a unique creation stamp per bundle (a request under contention is refused), and
  a global live-row cap (smaller for callers without an account, smaller still without a
  wallet). A reaper deletes bundles older than 7 days within an hour of their expiry; it is
  scheduled only while bundles exist, one one-shot at the oldest expiry, and runs at most
  once an hour. The client assembles the chunks (`ui/exportAssembly.ts`) and offers the file
  for download from the privacy overlay, which opens from the account overlay (`C`).
- **The starter.** A first `join_game` grants the starter monster and the kit in
  `game-core/content/starter_kit.ron` (200 gold, 2 Lure Berries, 1 Antidote), which
  `validate_starter_kit` checks at publish. The grant is recorded by the flag
  `sys:starter_claimed` (`npc::STARTER_CLAIMED_FLAG`) in the owner's private
  `player_dialogue_state.flags`, set in the same transaction as the kit;
  `onboarding::starter_grant(claimed, owns_monster)` is the rule. A kit that does not fit the
  stack and balance caps is skipped with a `starter_kit_skipped` log line and the flag stays
  unset. `validate_npc_content` refuses any dialogue condition or effect, quest start condition
  or quest step condition that names a `sys:` flag. The guest claim's `npc::rekey_npc_state`
  moves the dialogue row to the account and leaves the retired guest a tombstone row: its `sys:`
  flags, the starter flag and a copy of its done quests.
- **Tags and lead level.** The private `player_handle` table (`owner_identity` primary key,
  `discriminator: u32` `#[unique] #[auto_inc]`) is owned by `onboarding.rs`
  (`ensure_handle`, `rekey_handle`, `erase_handle`, `has_handle`). `join_game` finds the
  caller's row or mints one (insert 0, the column's sequence assigns the value), refuses the
  join with `handle unavailable` when the datastore refuses the mint, and copies the value
  onto the public `player.discriminator`. The claim moves the row (`rekey_all`), and a
  handle is game data (`account_has_game_data`). The deletion cascade erases the handle and
  zeroes `discriminator` and `lead_level` on the surviving `player` row; the export carries
  the handle row. `player.lead_level` is the stored level of the owner's lead party monster:
  `battle::refresh_lead_level` writes it only when the value differs, and the dual-write
  seam (`monster_mgmt::update_monster_synced`) calls it when a write changes a monster's
  `level` or `party_slot`; `join_game` and the session-trade transfer
  (`trading_session::apply_swap`) call it themselves. On the client `StorePlayer` carries
  `discriminator` and `leadLevel` apart from the raw `name`. `client/src/ui/playerTag.ts` is
  the one place a tag is formatted: `formatTag(discriminator)` gives `#` and the number
  padded to at least four digits through the catalog key `identity.tag` (no tag for 0), and
  `taggedName(players, identity)` joins the name and the tag through `identity.taggedName`
  (`Drew #0042`). The Social screen's Players row shows name, tag, lead level and Nearby,
  each its own element: the tag in `--mr-text-muted`, which the accessibility suite checks
  in both themes, except on the cursor row; the level through the battle HUD's
  `tactics.hud.level` copy so it reads the same in both places, and none for 0. The incoming
  trade and challenge request banner and the Trades-tab session row show the tagged name;
  the tactical battle clock, the trade editor heading, the rename view and the Rankings tab
  show the name alone. `playerName` (`client/src/ui/tradeSessionModel.ts`) shows `#` and the
  first eight hex digits of the identity when the store holds no row for it or the row's
  name is empty; that is not a tag (`validate_name` refuses an empty name at join and
  rename, so only an identity the store does not hold reaches it, and that identity has no
  tag to show).
- **Ranked PvP** will require accounts on both sides once a real issuer is set (`pvp.rs`
  `ranked_account_gate`). The gate reads `PRODUCTION_LOGIN_ISSUERS`, not the build's own
  `ALLOWED_ISSUERS`; until a real issuer is set it is inactive.

## Observability

- **Server.** The module emits JSON log lines. New code uses `observability::mr_log`;
  refusals go through `guards::log_reject`. A 60 s `mr_heartbeat` logs the deployed content
  version and writes nothing. In a world with nobody connected it is the only schedule but
  the hourly `host_account_check` tick, which runs only once the owner has named the host's
  identity, and it stays on purpose: it is the operator's dead-man's switch for the whole
  server (the `AlloyIngestStalled` alert reads ten minutes without module log bytes as a
  stalled log pipeline, and an empty world logs nothing else). Zone ticks and reapers are
  armed only while something needs them. The module never measures time itself and makes no
  outbound call but the account checks'; the SpacetimeDB host exposes `/v1/metrics` and
  writes module logs to files.
- **Stack.** `ops/observability/` is a Docker Compose stack on the host network,
  bound to loopback: Prometheus scrapes the host and node_exporter; Grafana Alloy
  tails the module logs into Loki and receives browser OTLP through Caddy, forwarding
  traces to Tempo and metrics to Prometheus; `mr-trace-relay` rebuilds server-side
  spans from paired log lines; Grafana (behind Caddy) queries all of them and handles
  alerting. Configuration checks run in `just test` (the `stack-config-checks` and
  relay node suites) and `just observability-validate` (upstream validators in the
  pinned images). Operations are in `docs/runbooks/observability-dr.md`.
- **Playtest capture.** The private `playtest_event` table records recruit attempts
  (`server-module/src/playtest.rs`); `playtest_reaper` keeps it under a 7-day TTL
  and a 20 000-row cap. It is scheduled only while events exist: one one-shot at the
  oldest event's expiry, pulled in to 5 minutes out when an insert takes the table over
  the cap. It runs at most once per 5 minutes, so an event is reaped within 5 minutes of
  its expiry. `just playtest-report` summarises it.
- **Load.** `sim-harness/src/bin/mr_load_driver.rs` is the load tool. Each bot holds what a walking
  client holds of `player` and `character`: `SELECT * FROM player`, byte-identical to the client's,
  plus its per-zone `character` queries. It holds none of the client's other tables, which walking
  does not write. The report gives each level's received bytes per client per second, as a mean and
  for the worst bot (`rx_bytes_per_client_per_s`, `rx_bytes_per_client_per_s_max`), over the
  driver's own scrape window. `MAX_CLIENTS` is 1,000. With `--fail-on-invalid`, an invalid level
  exits 3. The nightly `load-smoke` job publishes the `open_join` module build to an in-memory host
  and runs `just load-smoke` (20 clients, one level, `--fail-on-invalid`), so the nightly goes red
  when a level is invalid: no bot joins, a bot's zone scope never settles, or no move reaches the
  server. A level where every move is rejected stays valid, as a measurement of a saturated server.
  Runs over many zones use the load-only build from `just load-host` (`docs/DECISIONS.md`, "Dev-only
  reducers never ship"). Reducer-thread share is the recording rule
  `mr:reducer_thread_share:rate5m`, `sum by (reducer)
  (rate(spacetime_txn_elapsed_time_sec_sum[5m]))` (`ops/observability/rules/recording.rules.yml`).
  `promtool test rules` tests it under `just observability-validate`. The driver never runs in `just
  ci`; the nightly smoke is its one CI run.

| Server tests | `server-module/src/*_tests.rs`, including `native_host_tests.rs`, which runs reducers against an in-memory host: it defines the SpacetimeDB host ABI itself, and the patched copies under `vendor/` route the module SDK's native table calls to it (its guard test checks those copies against the crates.io release) | `just test` |
| Netcode | `sim-harness` plus the `netcode-determinism` and `netcode-convergence` evals | `just test`, `just eval` |
| Client unit tests | `client/src/**/*.test.ts` (vitest, happy-dom) | `just client-test` |
| Evals | `evals/*.eval.mjs`: wasm parity, feature isolation, determinism, schema and type snapshots, append-only ids, content version, bindings drift, client-surface privacy, sprite-sheet format, and the live account flow | `just eval` |
| Node suites | `ops/observability/**/*.test.mjs`, `scripts/*.test.mjs` | `just test` |
| Browser e2e | `client/e2e/*.spec.ts` (Playwright, two windows against a real SpacetimeDB and a `dev_reducers` build) | `just e2e`, CI `e2e-shard` jobs (one shard each; `e2e` checks their union is the whole suite) |

The module-definition check (`findDefinitionViolations` in
`scripts/verify-release-reducers.mjs`) reads what `extract-schema` prints and refuses an
HTTP handler, an HTTP route, a row filter, a procedure not in `ALLOWED_PROCEDURES` (the four
account checks in `account_checks.rs`), a schedule not in `ALLOWED_SCHEDULES`, at any
submodule depth, and any section kind it does not know. `just module-definition` (in `just
ci`) applies it to the default build and `just release-module` to each artefact it makes.
The reducer census in `privacy_enforcement_tests.rs` refuses a `procedure` attribute outside
`account_checks.rs`, and that file's `lpw34_7_unstable` module holds that the native test
binary links with `unstable` on.

The CI `e2e` job (`scripts/e2e-shard-union.mjs`) judges each shard by its highest attempt. When that
attempt's reports are readable, it also reads every lower attempt of the shard. A test that is
`unexpected` on a lower attempt and `expected` on the highest passed only on a rerun. The script
prints a `rerun-passed:` line and one `::warning` annotation for each such test. It also appends a
table of them to `$GITHUB_STEP_SUMMARY`, or "No e2e test passed only on a rerun." when there are
none, on a failing run too. A lower attempt with no readable `e2e.json` gets a `rerun-unreadable:`
line. The listing changes no verdict: a green highest attempt still passes the job. Playwright
`retries` is unset, so a rerun of failed jobs is the only second attempt, and a report's `flaky`
count stays a failure. `docs/e2e-flakes.md` registers the e2e flakes whose fix has not merged. Each
entry gives the test, the runs, the signature, every forcing recipe tried with its counts, the
verdict (product or test) and the next step. The change that fixes a flake deletes its entry. A test
the listing names that has neither an entry nor a residual row of its own is a new flake and gets an
entry. A flake that its own row holds may stay a row until a study takes it.

The native test host is `server-module/src/native_host_tests.rs`. A procedure runs through
`Fixture::run_procedure`: the host's `procedure_*` functions put an aborted transaction's rows
back and answer each HTTP request from a queue the test stubs. `ProcedureContext::sleep_until`
refuses natively; a native test of a procedure that sleeps adds two more `#[cfg]` attributes to
the patch and a `procedure_sleep_until` to the host.
`nh_vendored_crates_are_the_crates_io_release_plus_the_patch` proves each copy under `vendor/`,
with `vendor/native-host.patch` undone, matches the hashes in `vendor/PRISTINE.sha256`, and that
every changed line is a `#[cfg]` attribute selecting on wasm what the original selected; each
SpacetimeDB hop re-records them (`docs/runbooks/spacetimedb-upgrade.md`). CI's `cargo audit`
skips packages not from crates.io, so the two copies are checked at each hop by hand.

Mutation testing. The nightly `mutation` job runs game-core as six cargo-mutants `--shard k/n`
jobs, each its own zero-tolerance verdict. The pull-request job `mutation-diff` (`just mutate-diff
origin/master monster-realm-module`) mutates the server-module lines the change adds or edits,
diffed from the merge base, and fails on a survivor. The weekly `mutation-server` sweep (eight
shards) files its survivors as one issue on the default branch; a shard is red only when
cargo-mutants gave no verdict. An equivalent mutant is excluded in `.cargo/mutants.toml` with its
written proof; the bodies of `guards::log_reject`, `guards::json_escape`, `observability::mr_log`
and `mr_log_breadcrumb` are excluded by name.

`just ci` is the merge gate: lint, typecheck, test, eval, security, wasm,
client-typecheck, client-test, client-verify-build, and observability-validate.
`.github/workflows/ci.yml` runs the same recipes as parallel jobs grouped by
toolchain (`rust`, `eval`, `client`, `observability`), plus dependency review,
`cargo audit` and the sharded e2e jobs. Every job takes just, wasm-pack and the SpacetimeDB
CLI from `.github/actions/tools`: `scripts/ci-tools.sh` pins each version and archive
checksum, and the Actions cache serves the installed tools, wasm-pack's own downloads
and the Playwright browser, so a release-host outage does not fail a job.
