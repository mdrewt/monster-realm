# SpacetimeDB 2.6.0 → 2.8.1 — operator runbook

**Status: ✅ COMPLETED 2026-08-16** — CLI/host **and** Rust module crate both on 2.8.1, bindings
regenerated, all gates green. **Decision record:** [ADR-0197](adr/0197-spacetimedb-2.8.1-upgrade.md) ·
**Migration spec (executed):** `../../../specs/monster-realm-v2/M-stdb-2x-module-sdk.spec.md`

> **What this document is now.** It was written as a pre-flight plan; the upgrade has since been
> performed, so it stands as the **record of what was done and why**, with the predictions marked
> against what actually happened. §5 (what you gain) and §6 (what did *not* change) are the parts
> still worth reading day-to-day.
>
> **Outcome in one line:** the CLI, host and module SDK all moved 2.6.0/1.12.0 → 2.8.1; no table was
> renamed and no client code changed; `just ci` is green (1949 Rust tests, 87/87 evals, 2447 client
> tests). **⚠ One caveat that matters: an existing database CANNOT be republished in place** — 2.8.1
> renames every enum variant to lowerCamelCase, so a pre-bump DB needs `--delete-data`. See §3b.

---

## 1. The switch (done)

```bash
spacetime version use 2.8.1        # ~/.local/share/spacetime/bin/2.8.1
spacetime --version                # spacetimedb tool version 2.8.1  ✓
```

The Rust crate moved with it (`Cargo.toml`: `spacetimedb = "2.8.1"`), which required a mechanical
source port — three substitutions, 591 compile errors → 0:

| 1.x (old) | 2.x (now) |
|---|---|
| `#[table(name = X)]` / `#[view(name = X)]` | `accessor = X` |
| `ctx.sender` (field) | `ctx.sender()` (method) |
| `ctx.identity()` | `ctx.database_identity()` (old spelling is deprecated; CI runs clippy `-D warnings`) |

All **77** table names are byte-identical between the old 2.6.0-generated bindings and a fresh 2.8.1
generate, because the canonical SQL name defaults to the `accessor` identifier — **so the rename
itself is schema-neutral. A separate 2.8.1 change is not: see §3b.**

The module BINARY loads and runs unchanged. Verified from tagged source (ADR-0197):

- **Module ABI** — a 1.12.0-built module imports `spacetime_10.0`…`10.4`; the 2.8.1 host
  implements `10.5` and accepts any same-major module with a minor ≤ its own. `RawModuleDef`
  still accepts `V8BackCompat | V9 | V10`.
- **On disk** — snapshot MAGIC/version and commitlog MAGIC/format version are unchanged, so an
  existing local database survives the host upgrade.
- **Wire protocol** — `crates/client-api-messages` has *zero* changed files between 2.6.0 and
  2.8.1; the WebSocket subprotocol ids are identical. A 2.6.0 client can talk to a 2.8.1 server.
- **Automigration rules** — strictly *more* permissive (new `AutoMigrateStep::AddConstraint`).
  That is about the RULES; it does not save this particular republish, because the enum-variant
  rename is a type change no automigration step covers (§3b).

## 2. The two gates that went red, and how they were resolved (RESOLVED)

### 2a. `observability-metrics-contract` B4 "PIN MOVED" — RESOLVED

`.github/workflows/ci.yml` and `nightly.yml` pin `spacetime version install/use 2.6.0` in three
places. The eval compares that literal against the CLI on `PATH` and fails loud when they
diverge. **This is the tripwire working.** Its own message prescribes the fix:

> re-run the live half (`MR_OBS_LIVE=1`) against the new host, refresh the handoff evidence,
> then update the pin.

Done: the CI pins were moved to 2.8.1 **together with** the bindings regeneration, so the pin,
the committed bindings and the local CLI all agree. Editing the pin alone would only have moved the
divergence to CI.

### 2b. `bindings-drift` — RESOLVED

The committed `client/src/module_bindings/**` was generated by CLI 2.6.0 (the header literally
records `cliVersion: "2.6.0"`). A 2.8.1 `spacetime generate` differs. Measured with a real 2.8.1
CLI against this module: **exactly one file changes — `module_bindings/index.ts`, ~202 lines.**
No files added or removed, no per-table/per-reducer file touched.

The change is the 2.7.0 **camelCase** table/view handles plus the `cliVersion` literal.
**No client source changes are required** — snake_case survives as `@deprecated` runtime getters
*and* TypeScript types, and `tsc --noEmit` passes on all ~23 existing snake_case accessors.

Regenerated (`just gen`) and committed together with the CI pin bump. `npx tsc --noEmit` is clean
against the new bindings **while still on npm `spacetimedb` 2.6.0**, confirming the deprecated
snake_case aliases carry the existing ~23 accessors.

### 2c. CI pins moved with it

`.github/workflows/{ci,nightly}.yml` pinned `spacetime version install/use 2.6.0` in three places;
all three are now **2.8.1**, so CI generates with the same CLI that produced the committed bindings
and B4 agrees with the local toolchain.

## 3. What actually broke, and the fix that shipped (RESOLVED)

### `just playtest-publish` → `just playtest-verify-release` — FIXED

`scripts/verify-release-reducers.mjs` parses `spacetime describe --json` expecting the flat
`{"reducers":[…]}` (`RawModuleDefV9`) shape. **CLI 2.8.0+ emits `RawModuleDefV10` instead — and
this is a property of the CLI, not the host.** (`crates/cli/src/api.rs::module_def` requests
`version=10`; on a client error it falls back to `version=9` and *upgrades* the result to V10
before printing. So a 2.8.x CLI emits V10 even against an old host, and a 2.6.0 CLI emits V9 even
against a 2.8.1 host.)

```jsonc
// 2.6.0 (V9)                          // 2.8.0+ (V10)
{ "reducers": [ … ], "tables": [ … ] } { "sections": [ … ] }
```

Reducer entries also lose `lifecycle` and gain `source_name`/`visibility`/`ok_return_type`/
`err_return_type`. The parser matches neither candidate path and **throws** — loudly, as
designed (`SDK-10` in the migration spec).

**Shipped fix:** the parser now accepts both shapes, branching on the **payload shape** (never on a
probed version), with the fail-loud behaviour preserved. The V10 name field is **`source_name`**,
not `name` — captured from a live 2.8.1 instance, not inferred. V10 fixtures were added to
`evals/playtest-verify.eval.mjs` alongside the V9 ones (both the eval's mirrored reference
implementation and the real exported parser), and the eval caught the mirror being left behind.

## 3b. ⚠ Enum variant casing — the one thing that DOES require `--delete-data`

**Crate 2.8.1 emits sum-type variant names in lowerCamelCase; 1.12.0 emitted PascalCase.** The Rust
identifiers are untouched, so no source scanner, `schema-snapshot`, `spacetime-type-snapshot` or
`bindings-drift` can see it — but it is a change to the **column type** of every enum-typed column.
Reproduced by publishing the 2.8.1 module over a database published by the 1.12.0 module:

```
Changing the type of column affinity in table species_row
  from (Fire: () | Water: () | ...) to (fire: () | water: () | ...),
  with a renamed variant, requires a manual migration
Aborting because publishing would require manual migration or deletion of data
  and --delete-data was not specified.
```

Affected: `species_row.affinity`, `skill_row.affinity`, `account.status`,
`battle_challenge.status`, `trade_offer.status`, `character.direction`/`action_state`,
`npc.interaction`, `monster.nature_kind`/`trust_tier`, `battle.state`, … (`ScheduleAt`'s
`Interval`/`Time` are a library type and stay PascalCase.)

**What to do:** any database published before this upgrade — local playtest DBs, e2e fixture DBs,
`mr-acct-e2e` — must be republished with `--delete-data`, or dropped (`spacetime delete -y <name>`)
and recreated. `just playtest-reset` already does the `--delete-data` publish. This is acceptable
here only because the project is pre-launch; post-launch it would need a hand-written migration.

**The client is NOT affected** — `spacetime generate` emits the Rust identifier casing, so
`module_bindings/types.ts` is byte-identical to HEAD and `tsc` + 2447 client tests pass.

## 4. What to verify once, then stop worrying about

- **`mr-trace-relay` (ADR-0191).** 2.8.0 "reduced routine logs to quieter levels or module
  logs" for connection lifecycle, SQL queries, JWT lookups, migration planning and reducer
  errors. The relay pairs **module-emitted** `log::` breadcrumbs from `observability.rs`, which
  should be unaffected — **confirm, don't assume**. (`trace-pair-set.json` is currently an empty
  scaffold, so there is nothing live to break yet.)
- **Prometheus recording rules / dashboards.** No metric families were removed; several were
  added. `M20` OBS-9's "≥ 80 metric families" floor still holds (2.7/2.8 only add). Re-run the
  live half of the metrics contract to refresh the recorded evidence.
- **Reducer-arg CLI form.** ADR-0088 records that the 2.6.0 CLI takes each reducer argument as
  its own JSON value. Unchanged in the release notes, but the `spacetime call` path is exercised
  by `just playtest-*`; a smoke call confirms it.

## 5. What you gain (worth a look, none urgent)

| Capability | Version | Why you might care |
|---|---|---|
| `spacetime_scheduled_function_delay_seconds` + a late-start `log::warn!` | 2.8.0 | Direct visibility into `movement_tick` / trade + PvP reaper lateness. **The source threshold is 30 ms — the release note's "50ms" is wrong.** |
| `spacetime sql --format json` | 2.7.0 | The 2026-07-25 playtest gate recorded `just playtest-report` as non-functional partly because "the pinned CLI has no `--json` output mode". This may close that. |
| `spacetime lock` / `spacetime unlock` | 2.7.0 | Guard the playtest DB against accidental deletion. |
| View **primary keys** — available, **NOT yet adopted** | 2.6.0 (unlocked by the crate bump) | Lifts the "no view PK in 1.12.0" constraint that forced hand-rolled insert/delete reconciliation for `my_monster_pub` (ADR-0194) and shapes `15r-sec-a`. Nothing has adopted it: none of the five `#[spacetimedb::view(…)]` declarations carries `primary_key`, so `client/src/net/store.ts`'s hand-rolled reconciliation is still load-bearing. Adoption is tracked as the `M-stdb-2x-module-sdk` **sdk-d** opportunistic follow-up. |
| `#[unique]`/`#[primary_key]` on an existing table auto-migrates | 2.7.0 | Slightly relaxes ADR-0006/0173's additive-only discipline. |
| Scheduled intervals computed from the reducer's own `timestamp` | 2.7.1 | Removes accumulated drift on interval schedules — free correctness for the tick. |
| `spacetime mcp` | 2.8.1 | Live-DB MCP bridge for agents (`get_schema`, `sql`, `call`, `ping`). UNSTABLE; needs a running instance. Registration is documented in `.mcp.json`'s `$comment`. |
| **Procedures are STABLE in 2.x** (needs the crate bump) | ≤2.6.0 | **Corrects a false premise.** `#[procedure]`/`ProcedureContext` carry `#[cfg(feature = "unstable")]` at crate **1.12.0** but **not** at 2.6.0 or 2.8.1 — the gate this project sees is its own stale pin, not the platform. ADR-0180's 2026-08-08 amendment weighed "adopt a BETA SpacetimeDB API (scheduled Procedures with outbound HTTP, the `unstable` Cargo feature)" and **M20 OBS-48 forbids enabling `features = ["unstable"]`** partly on that basis. After the crate bump the beta objection evaporates: outbound HTTP from a scheduled procedure becomes a *stable* API. That does not automatically overturn OBS-48 (the ADR-0180 D14–D18 verdict also rested on `mr-trace-relay` being simpler and on not wanting an HTTP egress path in the module) — but it **must be re-adjudicated on the corrected facts** rather than inherited. **[RE-ADJUDICATED 2026-08-28 — Drew's ruling on https://github.com/mdrewt/monster-realm/issues/342: OBS-48 is now require-justification, not a blanket forbid. A use passes iff a committed `UNSTABLE_JUSTIFICATIONS` entry names the exact site, resolves to an ADR, cites the issue, pins the occurrence count and carries written reasoning; an unjustified use still fails CI. Recorded in ADR-0180's 2026-09-03 amendment. Note also that `#[procedure]`/`ProcedureContext`/`HttpClient` are themselves NOT `unstable`-gated at 2.8.1 — the two concerns are independent.]** |

## 6. What did NOT change (so nobody re-litigates it)

- **RLS is still not enforced.** `#[client_visibility_filter]` remains `unstable`-gated and
  still carries `// TODO: RLS filters are currently unimplemented, and are not enforced.` —
  byte-identical at crate 1.12.0 and 2.8.1. The private-table + owner-scoped `#[view]` pattern
  is the permanent design. The re-open triggers in M20 OBS-15/OBS-47, `validation-checklist`
  item 1, M6/M16/M19/M25 and `security-threat-model` **do not fire**.
- ~~Procedures are still `unstable`.~~ **WRONG — see §5. Procedures are stable in 2.x.**
- **There is still no module test framework.** GitHub issue #2833 is still open; there is no
  `spacetime test`. The pure-core + integration-harness split stands.
- **Rust modules still have no submodule support** — 2.8.0's submodules are TypeScript-only, so
  ADR-0055/0056's intra-crate split is unaffected.

## 7. Rollback

The CLI alone rolls back with `spacetime version use 2.6.0` — but that is **no longer sufficient**,
because the module crate and the committed bindings moved too. A full rollback is:

```bash
spacetime version use 2.6.0
git revert <this commit>          # restores crate 1.12.0, the 1.x source spelling,
                                  # the 2.6.0-generated bindings and the 2.6.0 CI pins
```

Table names, the wasm ABI major and the on-disk commitlog/snapshot formats are identical on both
sides, so the *host* rolls back cleanly. **But the enum-variant casing change (§3b) is directional
too**: after reverting the crate, republishing over a 2.8.1-created database will abort the same way,
in reverse. Roll back with `--delete-data` on any database created since the upgrade. Verify by
republishing and running `just eval`.
