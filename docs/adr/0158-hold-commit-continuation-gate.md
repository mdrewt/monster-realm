# 0158 — mvi: hold-commit tap/hold discrimination on the held-key continuation emitters

**Status:** Accepted
**Date:** 2026-07-27
**Slice:** movement-investigation (M-postgate-movement-investigation — r2 playtest ledger items 003/015/029/040-042)
**Supersedes:** —
**Amends:** 0148
**Subsystems:** movement-netcode, client-ui
**Decision:** Both held-key continuation emitters re-issue only via HeldDirections.committedActive(now): the active key must have been held >= HOLD_COMMIT_MS (150 ms, injected clock). Keydown's first step stays ungated. Pure not-emit.

## Context

Drew's THIRD residual movement report (r2): walk-to-edge, pause, single tap → sometimes 1 tile, sometimes 2. Diagnosed via a committed deterministic discrete-event sim (client/src/prediction/movementSim.test.ts, promoted from the diagnosis harness) driving the REAL Predictor/HeldDirections/reissueDir/characterToPredictedBaseline through a line-cited model of main.ts wiring + server reducers. Findings: (1) root cause CLIENT-side — the nh2/ADR-0148 continuation gate reopens when the server's movement_tick drain is observed, and the rAF loop re-issues if the key is still physically down; tick phase φ is uniform in [0, STEP_MS=200), so P(double) ≈ tapMs/200 for a 50–150ms human tap — the continuation decision depended on SERVER TICK PHASE, not player intent. (2) The edge is incidental (mid-map control reproduces identically); pause-then-tap is the trigger. (3) Server proven innocent: one drain per op, drains == accepted emissions, zero rejections (movement.rs:184-237) — pinned forward by the S1 matrix assertions. (4) This is exactly ADR-0148's accepted `{1,2}` tap-emission residual ("every 2 is a hold that genuinely spans a server tick"), now operator-reported as a defect — hence this ADR AMENDS 0148 rather than revising its mechanism. (5) The spec's observability fallback arm (E3) is explicitly NOT taken: the root cause was found and is reproducible; ADR-0157's dev-console reducer log already exists independently.

## Decision

heldKeys.ts stack entries carry `pressedAtMs` (stamps IN the entries — release()/clear() evict by construction, never a parallel map); `press(dir, nowMs)` nowMs REQUIRED (clockless press = compile error; forces future touch/gamepad input to supply a timestamp); `committedActive(nowMs)` returns the active (stack-top) dir iff held ≥ threshold; threshold is a constructor param defaulting to `export const HOLD_COMMIT_MS = 150`; main.ts changes exactly 3 lines (keydown press stamped with performance.now(); both emitters main.ts:450/:2139 swap held.active() → held.committedActive(now)); `const held = new HeldDirections()` stays argless. The dir-returning-method shape (vs a boolean conjunct in the guards) was a /simplify-lens reshape: it keeps every existing W-NH2 tooth byte-stable, deletes the `(0, now)` argument-revert mutant class, and enables the whole-file `held.active(` === 0 count tooth (partially closing ADR-0148 residual (b)).

**HOLD_COMMIT_MS = 150 — two-sided selection (record the sweep)**: CEILING — walk-start cadence: after the ungated first step drains, step-2's continuation must reach the server before the next tick or the server goes Idle for a slot (visible walk-start stutter, the ADR-0013 class nh2 protects): X + framePeriod(30fps) + latency < STEP_MS. Sweep (fps {24,30,60,144} × framePhase {0,.37,.61,.83}×period × tickPhase step 10 × latency {0,1,25}, hold-from-idle 2000ms): missedSlots=0 through X=160 but min step-2 slack 22.9ms at X=150 vs 3.8ms at 160, −3.3 at 170; selection rule 'largest X with zero missed slots AND slack ≥ 10ms, rounded down to 10' ⇒ 150. Fine-grid 30fps control: X=175 ⇒ slack −0.6 with a realized missed slot. FLOOR — tap coverage: maxSafeTap(X)=X measured, human taps 50–150ms ⇒ X ≥ 140. The two constraints CANNOT both cover 180ms presses (a red-team proposal to raise X to ≥200 was REJECTED: it breaks the 30fps walk-start budget — smoothness wins per ADR-0013). Resulting contract: taps ≤ 140ms ⇒ exactly 1 tile at every phase/fps; presses ≥ 240ms always walk (tests pin ≥260 for margin); (150, 240) is a declared indeterminate band. Switch-while-held measured harmless: the new key's drains stay at exact 200ms gaps in every phase (the emission time shifts; the drain time does not, since X+frame < 200). The budget is bound to the game-core SSOT mechanically by the new evals/hold-commit-step-budget.eval.mjs (reads the REAL STEP_MS from game-core/src/world.rs — a cadence retune reds CI until the threshold is re-derived; the unit pin U-H8 alone compares against a literal).

## Alternatives considered

(B) gate at press+STEP_MS — violates the cadence budget at every fps, guaranteed walk-start stutter; (C) release-cancel / clear_queue — ADR-0148 measured −1.75-tile backward snap in 9/10 release phases, local-clear = permanent freeze, tooth-forbidden (W-NH2-NO-CANCEL); (D) defer first step to keyup — destroys the ADR-0148 F3 freeze-escape and adds latency to every input; (E) server-side tap semantics — server proven correct, cannot see hold duration (latency-smeared arrivals re-introduce phase dependence), out of touch set; (F) debounce in sendIntent — gates the keydown by construction, breaks the e2e `__game().step()` hook, open-loop drift; (G) two gate-open observations — still phase-derived, fails the root cause; (H-boolean) `activeHeldAtLeast(ms, now)` conjunct in both guards — superseded by the committedActive reshape (argument-revert mutant class + tooth churn); (I) do nothing — operator reported it as a defect across 6 ledger items; (J) observability fallback — root cause found.

## Consequences / residuals

(1) taps in the (150,240)ms indeterminate band can still read as short walks — falsifiable prediction: if the next playtest still reports inconsistency, Drew's taps exceed 150ms and the next lever is NOT raising X (30fps budget forbids) but decoupling the two policies (allow one outstanding step once-committed) — parked follow-up. (2) Below 30fps the walk-start stutter returns (X is frame-rate-budget-bound; 30Hz is the in-contract floor per ADR-0148). (3) ADR-0148 residual 1b (ArrowRight+KeyD dual-code ungated keydown double) is now the SOLE remaining same-direction double-move path — out of scope here; a small fix (skip the first step when the dir is already held — does NOT break the F3 escape, which requires the dir NOT held) is recommended as slice `M-postgate-dualkey-dedup`. (4) No test executes main.ts's frame body: the sim proves the design, the W-teeth pin the wiring, neither proves runtime — mvi-e2e parked. (5) movementSim's ClientModel is a hand-maintained model of main.ts (drift risk disclosed in-file; strongest argument for (4)). (6) Touch/gamepad input: required nowMs makes a stampless press a compile error, not a silent never-walks. (7) A key held THROUGH a zone warp / reconnect / overlay-open is wiped by held.clear() exactly as pre-mvi (pre-existing; keydown does not refire on e.repeat), and the physical re-press now ALSO restarts the commit window — continuation resumes ~150ms later than pre-fix after such a wipe. (8) predictor.test.ts's runLoop model deliberately stays pre-mvi (it gates ADR-0148's outstandingSteps invariants; movementSim.test.ts is the authoritative post-mvi model — scope note in-file). (9) The e2e suite drives movement via `__game().step()`, bypassing held entirely: it cannot regress from this change and equally cannot prove it. (10) The overlay-visibility `||` chain remains duplicated 3× in main.ts (pre-existing SSOT smell, out of scope, noted for uxd3/overlay-registry). (11) Improvement over ADR-0148 residual 5: the measurement harness is COMMITTED this time (movementSim.test.ts).
